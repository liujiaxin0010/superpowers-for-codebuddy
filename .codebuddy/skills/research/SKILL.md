# 工程研究

用于在实现前输出一份**可验证、可追踪、只读**的研究结论，默认写入 `spec/AI2AI/research.md`。

## 输入

1. `spec/Me2AI/需求描述.md`
2. `spec/Me2AI/技术约束.md`
3. 目标模块路径（可选）
4. 用户明确关注的问题（可选）

## 硬约束

1. 只读分析，不修改业务代码、配置和测试
2. 先输出事实，再输出推断，最后输出未知项
3. 候选改动点可以列出，但**不能把实现方案伪装成研究结论**
4. 产出的 Markdown 文档内容默认使用中文（代码、命令、路径、字段名可保留英文）

## 研究判断框架

在下结论前，至少问自己：

1. 这条结论是**事实**还是**推断**
2. 它是否已经有直接证据支撑
3. 它对后续 spec / plan / execute 有什么影响
4. 它是否需要被写入 `findings.md` 复用

## 阻断条件

出现以下任一情况时，返回 `BLOCKED` 并说明缺什么：

1. `spec/Me2AI/需求描述.md` 与 `spec/Me2AI/技术约束.md` 同时缺失，且用户也没有给出明确研究目标
2. 仓库范围过大，但用户没有给出目标模块、目录或问题边界
3. 需要读取外部系统信息才能下结论，但当前没有访问条件

## 研究工作流

### 1. 确定研究范围

先明确以下问题：

1. 本次研究面向全仓、某个子系统，还是单一模块
2. 目标是理解架构、规范、边界、风险，还是定位候选改动点
3. 哪些结论必须有证据，哪些可以作为待确认项

### 2. 收集可验证事实

优先收集以下证据：

1. 目录结构、模块划分、入口文件
2. 配置文件、构建脚本、依赖声明
3. 关键接口、数据流、调用边界
4. 测试组织方式、测试命令、日志约束
5. 现有命名、分层、异常处理和文档习惯

### 3. 区分三类结论

- **事实**：能直接从代码、配置、目录、命令输出中验证
- **推断**：基于事实归纳出的判断，必须写清依据
- **未知项**：当前证据不足，必须由用户确认或后续补充

### 4. 提炼候选改动点

只列出**可能需要关注**的模块、文件或边界，不直接承诺实现方案。候选改动点应说明：

1. 为什么它与需求相关
2. 它影响的上游/下游边界
3. 继续深入前还缺什么信息

## 研究结束条件

满足以下条件时，研究可结束并交给下游：

1. 已明确研究范围和未覆盖边界
2. 已给出足够支持下游决策的事实
3. 推断都带有依据
4. 未知项已被显式列出
5. 下一步建议明确：继续 research / 写 spec / 请求确认

## 输出契约

研究报告至少包含以下部分：

```markdown
# 工程研究报告

## 研究范围
- 本次覆盖的目录/模块
- 未覆盖的边界

## 可验证事实
- 目录与入口
- 模块职责
- 接口/数据边界
- 测试与日志约束

## 推断与依据
- 推断结论
- 对应证据
- 信心等级：高/中/低

## 候选改动点
- 文件/模块
- 相关原因
- 潜在影响面

## 未知项
- 缺失信息
- 需要谁确认

## 下一步建议
- 推荐继续 research / 写 spec / 缩小范围 / 向用户确认
```

输出路径：`spec/AI2AI/research.md`

## 禁止事项

1. 不要只看单个文件就给出全局架构结论
2. 不要把“我猜测”写成“系统事实”
3. 不要直接下实现指令、改代码方案或任务拆解
4. 不要忽略日志、测试、配置这类非业务代码证据
5. 不要在证据不足时跳过未知项，必须显式标注
6. 不要为了“显得完整”把无关模块硬写进研究报告
