# Postgres SQL 最佳实践

本技能用于帮助 AI 在 PostgreSQL 场景里做**正确的技术判断**，而不是机械背诵一堆 SQL 示例。

## 何时使用

以下场景必须使用：

1. 编写或审查 PostgreSQL SQL
2. 设计表结构、索引、分页、批量写入
3. 排查慢查询、锁争用、长事务
4. 设计或优化 RLS 策略
5. 配置连接池或线上 DDL

## 资源加载规则

当需要看具体 SQL 例子、索引/锁/RLS 写法时，再读取：

- `references/query-patterns.md`

不要一开始就把整份示例文件读进上下文，先根据当前问题判断属于哪个类别。

## 决策规则

### 1. 先分问题类型

遇到 PostgreSQL 问题，先判断属于哪一类：

1. 查询慢
2. 写入/事务慢
3. 锁争用/死锁
4. RLS 或安全问题
5. 表结构/数据类型设计问题
6. 运维级变更，如索引、DDL、连接池

### 2. 查询慢时，按这个顺序想

1. 先看 `EXPLAIN ANALYZE`
2. 若出现大表顺序扫描，先怀疑索引缺失或条件不可索引
3. 若用了 `SELECT *`，先怀疑无效 I/O
4. 若出现大页码 `OFFSET`，先怀疑分页策略错误
5. 若业务层循环查库，先怀疑 N+1

### 3. 表结构设计时，先守住底线

1. UUID 用 `UUID`，不要用 `TEXT`
2. 金额用 `NUMERIC`，不要用 `FLOAT`
3. 高频过滤列、关联列、排序列才考虑索引
4. 复合索引按“等值列 -> 范围列 -> 排序列”思路设计

### 4. 并发和锁问题时，优先怀疑事务边界

1. 事务太长，会放大锁问题
2. 多事务对同一批行加锁顺序不一致，会导致死锁
3. 大表建索引要优先考虑 `CONCURRENTLY`

### 5. RLS 慢时，先怀疑策略写法

1. 策略中不要轻易套子查询或复杂函数
2. 优先直接使用会话变量
3. RLS 也是查询条件，照样需要索引思维

### 6. 连接问题时，先怀疑连接管理

1. 应用不应无池直连数据库
2. 连接泄漏比单次查询慢更致命
3. `max_connections` 不是越大越好

## 审查清单

编写或审查 SQL 时，至少检查：

1. `WHERE/JOIN/ORDER BY` 列是否有合理索引
2. 是否误用 `SELECT *`
3. 是否存在 N+1
4. 事务范围是否过大
5. 是否使用参数化查询
6. 大表 DDL 是否考虑 `CONCURRENTLY`
7. 分页是否误用 `OFFSET`
8. 批量操作是否仍逐条执行
9. RLS 是否破坏索引利用
10. 连接池与超时是否有基本边界

## 高风险反模式

1. 金额用 `FLOAT`
2. UUID 用 `TEXT`
3. 大页码分页继续用 `OFFSET`
4. 在应用层循环发 SQL
5. 大表 DDL 不考虑 `CONCURRENTLY`
6. RLS 策略里嵌复杂子查询
7. 依赖字符串拼接构造 SQL

## 禁止事项

1. 不要在没有 `EXPLAIN ANALYZE` 的情况下拍脑袋说“索引有问题”
2. 不要把所有列都加索引当成优化
3. 不要把 PostgreSQL 当成通用 SQL，不考虑其锁、RLS、连接特性
4. 不要忽略事务边界，只盯单条 SQL
5. 不要为了示例好看而复制大段无关 SQL
