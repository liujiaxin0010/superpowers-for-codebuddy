# 规则推断清单

本文件只在仓库缺少显式测试规则、或同一仓库存在多套风格时读取。

## 先看哪里

优先级从高到低：

1. 目标模块附近的测试
2. 同语言、同层级、同目录结构的测试
3. 仓库内数量更多的一侧
4. 通用最佳实践

不要直接拿无关模块的测试风格覆盖当前模块。

## 必须推断的关键项

1. 测试框架
2. 测试目录
3. 文件命名
4. 最低覆盖要求
5. Mock 策略

如果这些关键项里有任一项推不出来，默认 `BLOCKED`。

## 推断信号

### 框架

看：

1. 依赖文件
2. 测试入口 import
3. 常见断言函数与 lifecycle API

### 命名与目录

看：

1. `tests/`、`__tests__/`、`test/`
2. `_test.py`、`.test.ts`、`.spec.ts`、`Test.java`
3. 目标模块附近是否有强局部惯例

### Mock 策略

看：

1. 是否普遍 mock 数据库、HTTP、消息队列
2. 是否允许 spy 内部 helper
3. 是否通过 fixture / factory / builder 组织测试数据

## 冲突时的默认裁决

1. 局部模块惯例优先于全仓库平均
2. 显式规则优先于推断
3. 硬规则优先于软规则
4. 无法裁决时阻断，不要脑补

## 常见误判

1. 因为“仓库大多数用 tests/”就覆盖目标模块的 `__tests__/`
2. 因为模型更熟某个框架就改掉项目原框架
3. 把 snapshot 偏好误当成硬性规则
4. 把集成测试习惯误当成单测要求
