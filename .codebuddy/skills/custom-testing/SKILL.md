# 自定义测试方法论

本技能回答的是：**这个仓库的测试规则到底是什么，现在是否已经足够清楚到可以开始写测试。**

## 资源加载规则

当配置或任务上下文指定了 `external_test_rules` 时，必须先读取该外部规则文件，再继续任何测试生成。

当仓库缺少显式规则、或同一仓库存在多种测试风格需要推断时，再读取：

- `references/rule-inference-checklist.md`

当出现“多框架共存 / 外部规则与仓库现状冲突 / 硬规则与软规则纠缠”时，再读取：

- `references/rule-resolution-examples.md`

当用户要创建共享测试规则文件、且仓库里还没有现成版本时，再读取：

- `templates/external-test-rules-template.md`

当规则来自推断、或你做了冲突裁决时，再读取：

- `templates/rule-resolution-summary-template.md`

如果显式规则已经齐全，不要为了“多做一步”再加载推断参考。

## 何时使用

以下场景必须使用：

1. 项目已有明确测试规范
2. 用户要求“按项目约定”生成测试
3. 同一个仓库中存在特殊目录、命名、Mock 或覆盖要求

## 规则优先级

按以下顺序解释规则，后者不得覆盖前者：

1. 外部规则文件 `external_test_rules`
2. 本文件中的项目配置
3. 仓库里已存在的测试习惯
4. 通用测试最佳实践

若高优先级与低优先级冲突，以高优先级为准。

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 指定了 `external_test_rules`，但文件不存在
2. 同一规则出现冲突值，且无法判断哪个优先
3. 项目要求与现有测试框架明显不兼容，且用户未给出裁决
4. 在推断后，仍无法确认框架、目录、命名、覆盖要求或 Mock 策略中的关键项

## 规则类型

1. **硬规则**：框架、测试目录、命名模式、最低覆盖要求、禁止直连外部依赖
2. **软规则**：推荐分组方式、断言风格、是否偏好 spy、是否使用 AAA/GWT

硬规则冲突时必须阻断；软规则冲突时可以按仓库主流风格裁决，但要说明依据。

## 使用协议

### 1. 先读取规则

生成测试前必须先确定：

1. 使用什么测试框架
2. 测试文件放哪
3. 命名规则是什么
4. 最低覆盖要求是什么
5. 哪些依赖必须 mock，哪些不应 mock
6. 断言风格和清理策略是什么

### 2. 如果没有显式规则，再从仓库推断

优先看目标模块附近的现有测试，而不是先做全仓库平均。

### 3. 处理缺失或冲突规则

若缺少非关键规则，可以按现有仓库习惯补齐；若缺少关键规则，必须询问 Boss。关键规则包括：

1. 测试框架
2. 测试目录/文件命名
3. 最低覆盖要求
4. 外部依赖是否必须 mock

### 4. 生成测试时严格遵循

不得因为“模型习惯”擅自切换命名风格、目录结构或 Mock 策略。

### 5. 输出时说明采用了哪些规则

若规则来自推断而不是显式配置，必须说明：

1. 规则来自哪些现有测试文件
2. 哪些是硬规则，哪些是软规则
3. 是否存在仍待 Boss 确认的空白项

## 项目本地规则

如果本 skill 里已经维护了本地规则，至少要覆盖：

1. `framework`
2. `location`
3. `file_naming`
4. `branch_coverage`
5. `mock_*`

若这些字段未维护，则默认依赖 `external_test_rules` 或仓库推断。

## AI 的执行纪律

1. 先读规则，再写测试
2. 外部规则文件存在时必须优先读取
3. 命名、目录、Mock、断言风格必须服从项目配置
4. 不能用“默认更熟悉的框架”替换项目指定框架
5. 规则有歧义时，带着已确认信息向 Boss 提问
6. 若规则来自仓库推断，必须优先服从目标模块附近的现有测试

## 规则冲突处理

若显式规则与仓库现状冲突：

1. 先服从显式规则
2. 再在输出里标记“与现有仓库风格不一致”
3. 必要时建议 Boss 统一收口，而不是悄悄混用两套风格

## 与 TDD 的关系

本技能不替代 TDD：

1. TDD 决定先写测试还是先写实现
2. 本技能决定测试长什么样、放在哪里、覆盖到什么程度

## 禁止事项

1. 不要跳过规则读取直接按模型习惯写测试——模型默认偏好与项目规范不一致时会产生大量不合规测试
2. 不要把外部规则文件和本文件配置混着解释却不说明优先级——规则来源不透明会导致后续维护者无法判断哪条规则生效
3. 不要在项目要求 Jest 时擅自写成 Vitest，或反之——框架切换会导致配置、Mock API、断言语法全部不兼容
4. 不要在规则冲突时私自拍板——未经 owner 确认的裁决可能违反团队共识，引发风格分裂
5. 不要把”可选建议”当成”强制规范”——过度约束会增加不必要的修改成本和审查负担
6. 不要从无关模块的测试风格反推当前模块规则——不同模块可能有不同的测试策略，跨模块推断会引入错误约定
