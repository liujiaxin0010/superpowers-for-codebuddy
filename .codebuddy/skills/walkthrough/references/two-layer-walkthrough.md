# 两层串讲：议题清单与主持流程

## 为什么 AI 开发模式下串讲更重要

1. 人不再逐行读代码 → 设计阶段是人对质量影响最大的窗口，后面基本靠流程兜底
2. AI 不会主动对齐跨模块认知 → 串讲确保人的意图在编码前就达成一致
3. 方向偏了代价极大 → 方案先建好，后面就比较可控

## 概要设计串讲

- **时机**：方案设计完成后（`/spec-lite` / `/brainstorm` 之后）
- **关注点**：架构对不对、模块切得合不合理
- **参与**：全组 + 架构师 / 技术负责人（在引擎里即 Boss）

议题：

| 议题 | 要对齐什么 | 产出 |
|---|---|---|
| 架构方向对齐 | 分层架构（如服务层 + 任务层）、控制流/数据流划分 | 架构共识 |
| 模块边界确认 | 各组件职责边界，消除灰色地带 | 各组件职责表 |
| 核心机制共识 | 关键机制（如快照/缓存/并发策略）的取舍 | 机制共识 + 已知问题 |

## 详细设计串讲

- **时机**：详细设计完成后、编码前（`/write-plan` 之后）
- **关注点**：接口调得通不通、数据流对不对
- **参与**：模块负责人 + 关联方

议题：

| 议题 | 要对齐什么 | 产出 |
|---|---|---|
| 接口契约锁定 | 入参/出参/错误码逐字段对齐；跨格式转换映射表 | 接口契约表 |
| 数据流对齐 | 数据在模块间传递的格式、完整性 | 数据流图 |
| 联调风险消除 | 调用路径、重试策略、容错机制、Token/鉴权策略 | 联调风险与方案 |

## 主持流程

```
AI 梳理 spec → 列出本层议题清单
   │
   ▼
逐议题展示：现状 + AI 的理解 + 可选方向
   │
   ▼
Boss 逐项确认 / 质疑（AI 对质疑给技术论证或接受修正）
   │
   ├─ 确认 → 记入纪要「结论」+ 标 ✅ Boss 确认
   └─ 未决 → 落 pending-decisions（≥2 项即强制）
   │
   ▼
产出串讲纪要（committed）→ 回填 spec-lite 追踪字段
```

要点：
- 一次过一个议题，不要一次抛一堆让 Boss 难以聚焦
- 接口契约必须精确到字段；内部实现路径留白（意图驱动，不规定语法）
- 纪要每条结论标注是否经 Boss 确认——未确认的不算对齐
