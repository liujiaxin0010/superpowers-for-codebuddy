# 头脑风暴阶段指南

本文件提供每个阶段要收集的信息、推荐提问方式和结束条件。主 `SKILL.md` 只负责路由和节奏控制；真正推进阶段时，按本文件执行。

## 使用方式

1. 一次只读取当前阶段
2. 先问一个问题，再给一段阶段小结
3. 当前阶段未确认前，不进入下一阶段

## 阶段一：背景与需求功能点

### 目标

明确需求为什么存在、谁会使用、功能点边界在哪里。

### 必收信息

1. 背景：业务驱动、客户反馈、竞品压力、内部演进
2. 使用者：谁来用、在什么场景使用
3. 功能点：一级功能、二级功能
4. 优先级：当前必须交付什么，哪些可后置

### 推荐提问方式

优先使用单选或少量枚举题，再用表格回显：

```text
Boss，我先确认这个需求的驱动因素：
A) 客户明确提出
B) 竞品已有，需跟进
C) 内部技术演进
D) 其他
```

### 阶段结束条件

1. 背景已确认
2. 功能点列表已回显并经 Boss 确认无遗漏

## 阶段二：应用组网与竞品分析

### 目标

明确系统部署关系、外部环境、竞品对比和营销亮点。

### 必收信息

1. 应用场景和组网拓扑
2. 竞品现状与优劣对比
3. 专利风险或知识产权风险
4. 竞争优势和营销亮点

### 输出要求

1. 需要组网时，用 Mermaid `graph LR` 或 `graph TD`
2. Boss 不了解竞品时，明确标记“待补充”

### 阶段结束条件

1. 组网关系已确认
2. 竞品分析已确认或被显式标记待补充

## 阶段三：技术分析与方案选型

### 目标

让 Boss 在 2-3 个方案中选择，而不是直接推进单一路径。

### 必收信息

1. 技术难点
2. 候选方案 2-3 个
3. 每个方案的收益、代价、风险、工期
4. 工作量预估

### 推荐输出格式

```text
方案 A：思路 / 优势 / 劣势 / 工期
方案 B：思路 / 优势 / 劣势 / 工期
方案 C：思路 / 优势 / 劣势 / 工期
```

### 阶段结束条件

Boss 已明确选择方案，或明确要求保留多个备选方向。

## 阶段四：软件设计（分段确认）

### 目标

把关键设计拆成小段确认，避免一次性抛出大块设计。

### 子阶段

1. 接口设计
2. 界面设计
3. 关键业务流程
4. 数据库设计
5. 可维护性设计
6. 高可靠性设计
7. 产品化设计
8. 全局配置开关

### 子阶段 1「接口设计」—— 平台类 OpenAPI 接口联动协议

判断本次设计的接口是否属于**平台类 OpenAPI 接口**（对外 RESTful 接口、URL 形如 `/openAPI/{serviceURI}/v1/...`）：

- **是平台类 OpenAPI 接口**：接口设计必须遵循 `openapi-creator` 技能的规范，不得随意设计。
  1. 读取 `.codebuddy/skills/openapi-creator/references/openapi-spec.md` 与 `.codebuddy/skills/openapi-creator/SKILL.md` 的「生成规则」
  2. 头脑风暴阶段只确认「接口清单 + 关键业务字段」草案，并按生成规则约束草案：命名 lowerCamelCase、数据类型仅 integer/number/string/array/object、URL 格式、HTTP 方法 POST、分页 pageNo/pageSize/total、批量 successList/failureList、数组 List 后缀、字段标准引用等
  3. 头脑风暴阶段**不**展开 openapi-creator 的完整五阶段流程
  4. 在阶段小结中标注：正式的接口定义文档生成、规范校验、YAML 导出，在头脑风暴结束后通过 `/openapi` 命令完成
- **非平台类 OpenAPI 接口**（内部模块接口、SDK 接口等）：按常规接口设计确认，无需联动 openapi-creator

### 关键提醒

1. 每个子阶段展示后都要确认
2. 业务流程统一用 Mermaid
3. 日志方案必须说明框架、字段、级别、traceId、英文日志、控制台输出边界
4. 接口设计子阶段若涉及平台类 OpenAPI 接口，必须执行上方「OpenAPI 接口联动协议」

### 阶段结束条件

2.5.1 到 2.5.8 都已逐段确认或标记待补充。

## 阶段五：检查清单与合规

### 目标

显式确认安全、法规、开源、配套影响等检查项。

### 必收信息

1. 鉴权、异常保护、安全风险
2. 端口、传输、密码、敏感信息
3. 法规、敏感词、隐私要求
4. 开源库变更与协议风险
5. 对其他组件的影响

### 推荐方式

逐项确认，而不是笼统询问“还有没有合规问题”。

### 阶段结束条件

检查项被明确标记为“已确认 / 不适用 / 待补充”。

## 阶段六：跨模块与兼容性分析

### 目标

覆盖影响面、兼容性、升级和平滑演进风险。

### 必收信息

1. 系列产品与终端产品影响
2. API/SDK/设备/域间兼容性
3. 平滑升级方案
4. 外部依赖与特性依赖

### 输出建议

升级方案优先用 Mermaid `graph TD` 画升级流程。

### 阶段结束条件

影响面和兼容性已明确；不确定项必须标记“待评估”。

## 阶段七：收尾评估

### 目标

补齐重用、性能、遗留缺陷、估计与风险。

### 必收信息

1. 重用分析
2. 性能目标
3. 遗留缺陷
4. 代码规模、人力、测试工作量、风险

### 阶段结束条件

Boss 确认所有收尾评估信息，或接受保留待补充项。

## 文档生成规则

1. 生成文档前，必须完整读取 `requirement-doc-template.md`
2. 模板中的章节标题不得删除
3. 未确认信息标记 `<!-- TODO: 待补充 -->`
4. 所有图表统一使用 Mermaid
5. 文档生成后必须展示给 Boss 做最终确认
