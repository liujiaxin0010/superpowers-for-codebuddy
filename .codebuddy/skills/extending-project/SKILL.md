# 项目功能扩展

本技能用于回答一个更具体的问题：**在不破坏现有系统的前提下，应该怎么把新功能接进去。**

## 何时使用

以下场景优先使用：

1. 在已有项目上新增功能
2. 需要先判断是新增模块还是修改现有模块
3. 需要控制改动面、回归风险和日志一致性

## 何时不用

以下情况优先考虑其他技能：

1. 纯修 bug：优先 `bug-fix`
2. 纯重构：优先 `writing-plans` / `executing-plans`
3. 需求仍然模糊：优先 `brainstorming` 或 `spec-lite`

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 需求目标、范围或入口不明确
2. 无法确定当前项目的核心架构和日志约束
3. 需要大范围改共享契约，但 spec/plan 尚未明确

## 持久化记录要求

每次执行 `/extend` 都必须：

1. 至少更新一次 `docs/progress.md`
2. 如有技术判断、分流决策或风险结论，同步更新 `docs/findings.md`

## 扩展工作流

### 1. 先理解项目

至少确认：

1. 项目类型、技术栈、目录约定
2. 核心入口和依赖关系
3. 测试方式
4. 日志框架、字段结构、控制台输出边界

### 2. 再做影响评估

输出三类结论：

1. 必须新增的文件/模块
2. 必须修改的现有文件
3. 应保持不动的核心模块

### 3. 决定扩展模式

优先按以下思路选择：

1. 新增路由/处理器，而不是直接改原路由
2. 新增页面/组件，而不是把新逻辑塞进旧组件
3. 新增独立模块，通过接口接入
4. 只有在确实必要时，才修改现有类或共享契约

### 4. 再进入计划和执行

扩展任务在进入实现前，必须：

1. 明确“新增”与“修改”的边界
2. 每个修改类任务标注风险等级
3. 每步都保留回归验证命令

## 扩展设计原则

1. **高内聚**：新功能代码尽量集中在独立模块
2. **低耦合**：通过清晰接口与现有系统交互
3. **加法优先**：先新增，再接入，最后才考虑最小修改
4. **日志一致**：沿用现有日志结构，不引入中文日志和随意控制台输出

## 风险检查

扩展前后重点检查：

1. 是否改动了共享契约
2. 是否影响原有测试主路径
3. 是否引入循环依赖
4. 是否把临时逻辑散落进多个旧文件

## 禁止事项

1. 不要在没搞清架构前直接改代码
2. 不要把“扩展”写成对现有模块的大面积侵入式改造
3. 不要跳过回归验证
4. 不要忽略日志结构和观测约束
5. 不要把高风险共享修改伪装成“小改动”
