# 扩展阶段参考

本文件只在已经确认要做“项目功能扩展”后读取。按当前卡住的阶段读取，不要整份通读。

## 理解项目阶段

至少确认：

1. 用户入口在哪里
2. 核心编排链路如何串起来
3. 哪些目录属于稳定核心，哪些目录允许频繁扩展
4. 日志、指标、错误处理是否有统一约定

重点产出：

1. 新功能最可能的接入点
2. 最可能被误改的共享模块
3. 最小可跑的验证路径

停手信号：

1. 连入口与主路径都还没找清
2. 不知道日志/观测约束，却已经准备写新逻辑

## 影响评估阶段

评估时强制分成四类：

1. 必须新增
2. 必须修改
3. 应保持不动
4. 待 owner/Boss 确认

重点检查：

1. 是否触及共享契约、公共模型、核心配置
2. 是否会影响现有测试主路径
3. 是否会把一个新增功能拆成多个旧文件里的侵入式修改

停手信号：

1. “必须修改”的文件越列越多，但没有清晰的共因
2. 你无法说清某个核心模块为什么一定要动

## 扩展模式选择

优先级从高到低：

1. 新增独立模块，通过现有接口接入
2. 新增路由、处理器、页面、任务编排层
3. 在现有模块上做最小修改
4. 修改共享契约或核心抽象

适用提醒：

1. 如果新能力只影响一条边缘链路，优先加法，不要反推重写中心模块
2. 如果多个接入点都可行，优先选最少共享修改、最容易回归验证的那条

停手信号：

1. 你为了“更优雅”想先重构底座
2. 还没证明现有扩展点不够用，就准备改共享抽象

## 日志与观测接入

新增功能时优先复用：

1. 现有 logger
2. 现有字段结构
3. 现有错误码、trace、request id 约定

不要做的事：

1. 随手加中文控制台输出
2. 新旧链路混用两套日志字段
3. 只补业务逻辑，不补最基本的观测点

## 常见误判

1. 把“新增入口”误做成“修改核心流程”
2. 把“少量共享修改”扩大成“顺手统一架构”
3. 以为文件改得少就是低风险，却忽略了共享契约
4. 新功能代码散落在多个旧文件里，最后没有清晰 owner
