# 接收代码审查反馈

本技能关注的不是“礼貌”，而是**如何诚实、可验证地处理审查意见**。

## 资源加载规则

当你不能立刻判断“同意 / 部分同意 / 不同意 / 暂不确定”时，再读取：

- `references/review-decision-matrix.md`

当需要按统一格式逐条回复 review 意见时，再读取：

- `templates/review-response-template.md`

不要一开始就把模板内容原样复制给审查者；先做验证和判断，再按模板组织回复。

## 阻断条件

出现以下任一情况时，先 `BLOCKED` 或升级给 Boss / owner，而不是仓促表态：

1. 原始 review 意见缺少位置、范围或上下文，无法判断在说什么
2. 高严重度意见无法复现，且现有证据不足以支持同意或反驳
3. 需要修改共享契约、公共 API 或方向性设计，但当前没有 owner 裁决
4. 还没有最小验证路径，却准备直接回复“已修复”或“不同意”

## 核心协议

1. 先验证，再表态
2. 用行动和证据回应，不用赞美代替思考
3. 同意、部分同意、不同意都可以，但都要有技术依据

## 处理流程

1. 先理解 review 的位置、严重度和建议方向
2. 再选证据类型：复现、测试、基准、静态契约推理、代码走读
3. 再决定结论：同意 / 部分同意 / 不同意 / 暂不确定
4. 再决定动作：修复、替代方案、升级裁决、补更多验证
5. 最后判断是否需要 re-review

## 严格禁令

禁止表演性赞同，例如：

- "You're absolutely right!"
- "Great point!"
- "完全正确！"
- "非常好的建议！"

## 输出建议

逐条回复时至少包含：

1. 原始反馈
2. 严重度
3. 评估结论
3. 技术依据
4. 修复或替代动作
5. 验证证据
6. 是否需要 re-review

## 优先级

1. 严重：先验证、先处理、先决定是否要 re-review
2. 警告：当前轮次尽量闭环
3. 建议：至少说明是否采纳和理由

## 常见反模式

1. 不解释就标记“已修复”
2. 不验证就争论
3. 机械应用所有建议
4. 忽略建议级反馈
5. 修完不跑测试
6. 借回复 review 之名顺手做无关重构

## 收尾要求

修复完成后至少要做到：

1. 运行测试并展示证据
2. 逐条说明处理结果
3. 明确是否需要重新审查
4. 若仍有争议，明确下一步由谁裁决

## 禁止事项

1. 不要用赞美替代技术判断——“Great catch!” 不是回复，证据 + 结论才是
2. 不要在无证据时说”这个 review 不对”——反驳需要复现结果或基准数据，不是直觉
3. 不要机械照单全收——盲目应用不理解的建议会引入新 bug，比忽略更危险
4. 不要修完不验证——“已修复”没有附带测试结果 = 没有修复
5. 不要跳过严重问题直接进入下一个任务——严重问题未闭环时后续任务建立在不稳定基础上
6. 不要把 review 意见当作绝对权威——reviewer 也会犯错，独立验证是你的责任
7. 不要在回复中混入无关重构——借 review 之名扩大修改范围会引入新风险并模糊 diff
