# 接收代码审查反馈

本技能关注的不是“礼貌”，而是**如何诚实、可验证地处理审查意见**。

## 核心原则

1. 先验证，再表态
2. 用行动和证据回应，不用赞美代替思考
3. 同意、部分同意、不同意都可以，但都要有技术依据

## 严格禁令

禁止表演性赞同，例如：

- "You're absolutely right!"
- "Great point!"
- "完全正确！"
- "非常好的建议！"

## 处理协议

### 1. 理解

明确：

1. 审查者指出了什么
2. 严重程度是什么
3. 建议的修复方向是什么

### 2. 验证

对问题本身做独立验证：

1. bug 类意见：写测试或重现
2. 性能类意见：跑基准或定位瓶颈
3. 命名/结构类意见：评估是否真的影响理解

### 3. 评估

把每条意见归为：

1. 同意
2. 部分同意
3. 不同意
4. 暂不确定

每一类都要说明理由。

### 4. 行动

1. 同意：修复并验证
2. 部分同意：给出替代方案并验证
3. 不同意：提交技术证据，请 Boss 裁决
4. 不确定：说明不确定点，请 Boss 决策

## 输出建议

逐条回复时至少包含：

1. 原始反馈
2. 评估结论
3. 技术依据
4. 修复或替代动作
5. 验证证据

## 优先级

1. 🔴 严重：优先处理
2. 🟡 警告：当前轮次尽量处理
3. 🔵 建议：至少给出是否采纳和理由

## 常见反模式

1. 不解释就标记“已修复”
2. 不验证就争论
3. 机械应用所有建议
4. 忽略建议级反馈
5. 修完不跑测试

## 收尾要求

修复完成后至少要做到：

1. 运行测试并展示证据
2. 逐条说明处理结果
3. 明确是否需要重新审查

## 禁止事项

1. 不要用赞美替代技术判断
2. 不要在无证据时说“这个 review 不对”
3. 不要机械照单全收
4. 不要修完不验证
5. 不要跳过严重问题直接进入下一个任务
