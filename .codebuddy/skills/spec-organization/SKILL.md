# 规格文档组织（Spec Organization）

本技能回答的是：**设计文档该怎么分层、放哪、命名、保持与代码同步，让 AI 沿目录与链接精准定位、减少幻觉。**

## 核心心智

1. **双层 Spec**：高层 Spec（概要，面向人，指导架构方向）+ 低层 Spec（详细，面向 AI，作为代码生成的直接输入）。高层保方向正确，低层保生成精准。
2. **唯一事实来源**：组件级规格与代码同仓（`spec/` 目录），禁止多份副本，更新后立即提交。
3. **先固化再迭代**：聊天中的设计结论必须及时固化为文档——未固化的知识等于不存在的知识。
4. **文档链接构建知识网络**：通过相对路径链接建立引用关系，帮 AI 沿链定位，减少幻觉。

## spec/ 三级目录结构

组件级设计随代码仓库在 `spec/` 下管理；系统级顶层设计独立仓库维护。完整目录结构、文件说明、命名规范见 `references/structure-spec.md`。

## 资源加载规则

- 判断目录结构 / 命名 / 做结构合规检查时，读 `references/structure-spec.md`
- 处理唯一事实来源 / SSoT 错误 / Merge-Back 回填时，读 `references/ssot-principles.md`
- 在文档里画图时，读 `references/mermaid-conventions.md`
- 写具体设计文档时，读对应 `templates/`：`readme-l1/l2/l3.md`（子系统/子组件/子模块）、`tech-selection.md`、`core-flow.md`、`db-design.md`、`config-design.md`（OpenAPI 用 `openapi-creator`）

## 何时使用

1. 任务从「轻量规格」升级为组件级，需要建立完整 `spec/` 结构
2. 编写 README / 技术选型 / 核心流程 / 数据库设计 / 配置设计文档
3. 检查既有 `spec/` 是否结构合规（`/spec-check`）

## 何时不用

1. L 级单文件小改——`spec-lite` 的轻量 `docs/specs/*.md` 足够，不必上重结构
2. 纯代码自文档（CONTEXT.md）——那是 `code-documentation` / `doc-sync` 的职责，与 `spec/`（设计文档）是两套体系

## Spec 细致度判断

写 Spec 时自问三个问题，三个都是 Yes 才合格：

1. **架构约束**：能否约束 AI 代码的模块边界、调用方向、依赖关系？
2. **测试指导**：能否直接转化为测试用例？验收标准是否明确？
3. **无需澄清**：另一个开发者不经澄清能否实现？

**Spec 细致度上限 = Test 覆盖度**。各层级合理细致度：L1 顶层粗到能约束方向、禁区清晰；L2 系统级规则条目化、反面案例有力；L3 组件级 API 合约锁死、其余可松；L4 模块级最需细，但**永远不写具体函数名/变量名**（意图驱动，不规定语法）。

## 与 spec-lite 的关系（毕业路径）

- `spec-lite`：轻量入口，产物在 `docs/specs/*-spec-lite.md`（flat），适合 L/M 小任务
- `spec-organization`：当任务是组件级、需长期演进时，把设计「毕业」到完整 `spec/{子组件}/...` 结构
- 不强制小任务用重结构——按需升级

## 禁止事项

1. 不要把设计结论只留在对话里——文档私藏，换 session 即丢失（SSoT 错误）
2. 不要用代码注释代替规格——注释随代码老化失效（SSoT 错误）
3. 不要让同一需求有多份不一致文档——规格分裂，AI 行为矛盾（SSoT 错误）
4. 不要在低层 Spec 写死函数名/变量名——过度规定实现会约束 AI 优化空间
5. 不要在子目录（核心流程/、测试用例/、配置设计/）放 README.md——这些目录本身不需要 README
