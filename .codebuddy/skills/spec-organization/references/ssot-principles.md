# 唯一事实来源（SSoT）与 Merge-Back

## 唯一事实来源原则

组件级规格与代码同仓存放（`spec/` 目录），确保规格与实现始终同步。系统级设计独立仓库维护。**禁止多份副本，更新后立即提交，确保任何时刻只有一份权威文档。**

规格与代码同仓的天然优势：MR/PR 可以同时包含代码变更和规格更新，缓解文档腐化。

## 三种 SSoT 错误（必须警惕）

| 错误类型 | 表现 | 后果 |
|---|---|---|
| 文档私藏 | 规格只存在于 AI 对话历史，未回填 `spec/` | 换 session 后规格丢失，后续开发无据可依 |
| 代码即文档 | 用代码注释代替规格文档 | 规格随代码老化失效，注释与实现逐渐脱节 |
| 规格分裂 | 多个文档描述同一需求但内容不一致 | AI 产生矛盾行为，不同 session 产出不一致 |

## Merge-Back 回填机制

开发过程中的临时规格（如对话结论、OpenSpec 临时补丁、`spec/AI2AI/` 过程文档），验证通过后**必须回填至 `spec/` 目录下的主文档**。回填后临时规格升级为「官方规格」，确保文档永远是代码的实时快照。

```
方案设计（创建 Spec）→ 编码实现（Spec 驱动代码）→ 规格回填（代码反哺 Spec）
        ↑                                                  │
        └────────── 下一个迭代从更新后的 Spec 出发 ←────────┘
```

回填的三层保障（即时/每日/每周）与三段式写作规范由 `spec-backfill` 技能落地；本文件只定义「为什么必须回填」与「回填到哪」。

## 文档生命周期管理

Spec 存在自然腐化：项目初期作用显著，随迭代累积偏差增大。应对：

- **编码阶段**：每次生成代码后同步更新 `spec/` 相关文档（尤其核心流程和接口定义）
- **审查阶段**：代码审查时同步检查 Spec 是否需更新，将 Spec 偏差视为技术债
- **长期方向**：由 AI 根据最新提交自动检测并更新（`spec-backfill` + `scheduled-automation` Task#1/#25）

## 诚实性

实现与 Spec 偏差时，不删除 Spec 也不隐瞒差异，而是在文档中**显式标注**（如「filemetrics 模块实际用 JSON 文件持久化而非 DuckDB」），让后续开发者（含 AI）了解真实状态。
