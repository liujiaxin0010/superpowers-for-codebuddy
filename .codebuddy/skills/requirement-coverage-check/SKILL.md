# 需求覆盖审查（Requirement Coverage Check）

回答的核心问题：**AI 写出来的代码到底有没有把需求文档里的每一项都做对、做完、不多不少？**

定位：这是**系统测试之前**的最后一道独立审查门。它不替代单元测试、不替代代码风格审查，只做一件事——把"需求项"逐条和"代码 + 验证用例"做对账。

## 何时使用

1. `/execute-plan` 已声明完成，准备进入 `/unified-test` 或系统测试前
2. 需要在合并 / 提测前对齐"做的是不是用户要的"
3. 用户明确要求"评审 AI 写的代码与需求文档差异"
4. 任何 H 级 / 复杂扩展任务的强制收口前置

## 何时不用

1. 没有需求分析文档或覆盖矩阵——先回 `/brainstorm` 或 `/spec-lite`
2. 单纯想看代码风格问题——用 `/code-review`
3. 单纯想看 diff 是否安全——用 `/code-self-check`

## 阻断条件（任一满足即 BLOCKED）

1. 找不到需求分析文档（`docs/plans/<...>-需求预分析.md` 或 `docs/specs/<...>-requirement-analysis.md`）
2. spec / plan 中缺少"需求覆盖矩阵"
3. 当前分支无可执行代码（实现尚未发生）
4. 验证用例缺失，无法证明任一需求项已实现

## 输入参数

`/requirement-coverage requirementDoc=<path> [specDoc=<path>] [planDoc=<path>] [vcs=auto|git|svn]`

## 制度化的不信任原则

**禁止信任实现者的"已完成"声明。** 必须独立打开代码、独立运行验证用例、独立比对需求项。规则：

- 实现者说"REQ-01 已完成" → **打开代码定位实现位置 + 运行 TC-01 看输出**
- 实现者说"全部覆盖" → **逐行审矩阵，缺一即失败**
- 实现者说"额外加了 X 优化" → **检查是否在需求项内；超出即 YAGNI 违规**

## 执行流程

### 第一步：加载需求与矩阵

1. 读取需求分析文档，提取全部 `REQ-*` 项
2. 读取 spec / plan 中的"需求覆盖矩阵"
3. 形成检查清单：每个 REQ 必须能定位到 `实现位置` 与 `验证用例 ID`

### 第二步：逐项验证

对清单的每一项执行：

```text
1. 打开"实现位置"（文件:行号 或 函数）
2. 阅读对应代码，判断：
   a. 是否实现了"需求描述"声明的能力？
   b. 是否实现了"需求描述"声明的边界 / 异常 / 非功能约束？
   c. 是否引入了需求外的副作用？
3. 运行"验证用例 ID"对应的测试或可执行命令
4. 记录结果：
   ✅ 完全满足 / ⚠️ 部分满足 / ❌ 未满足 / 🟠 越界实现
```

### 第三步：差异归类

| 类别 | 含义 | 处置 |
|---|---|---|
| 🔴 缺失实现 | 需求项无对应代码 / 测试 | 阻断系统测试，回退实现 |
| 🟠 越界实现 | 代码做了需求外的事（含兼容性代码） | 阻断，删除或回退 |
| 🟡 部分满足 | 主路径对，但边界 / 异常 / 非功能约束未覆盖 | 当轮修复 |
| 🟢 偏差但合理 | 与需求文字不同但业务等价（罕见） | Boss 显式确认后通过 |
| ✅ 完全满足 | 实现 + 验证均通过 | 放行 |

### 第四步：输出审查报告

报告路径：`docs/quality/requirement-coverage-report.md`
缺陷汇总：`docs/quality/requirement-coverage-report.xlsx`（复用 `xlsx` 技能）

报告必须包含：

```markdown
# 需求覆盖审查报告

- 审查日期：YYYY-MM-DD
- 需求分析文档：<path>
- 覆盖矩阵：<path>
- 当前 commit：<sha>
- 审查结论：通过 / 不通过

## 覆盖统计

| 状态 | 数量 |
|---|---|
| ✅ 完全满足 | N |
| 🟡 部分满足 | N |
| 🔴 缺失实现 | N |
| 🟠 越界实现 | N |
| 🟢 偏差但合理（已 Boss 确认） | N |

## 逐项审查明细

### REQ-01 [需求描述简写]
- 实现位置：`path/to/file:line`
- 代码摘要：[3-5 行核心代码或描述]
- 验证用例：TC-01
- 验证证据：
  $ <run command>
  <stdout>
- 判定：✅ / 🟡 / 🔴 / 🟠
- 说明：

...（每个 REQ 一节）

## 越界 / 兼容性代码扫描

- 是否新增了未在需求文档中声明的依赖？
- 是否新增了浏览器 / 旧版本兼容 polyfill？
- 是否在需求外文件做了"顺手优化"？

## 结论与下一步

- 通过 → 推荐 `/unified-test` 或系统测试
- 不通过 → 列出阻断项 + 退回命令（`/execute-plan` 修复 / `/fix-bug` / `/code-self-check applyFix=true`）
```

## 与其他技能的协作

| 技能 | 关系 |
|---|---|
| `spec-reviewer` 子代理 | 本技能复用其"制度化不信任"原则；可在第二步并发调用 |
| `code-review-standards` | 本技能不审风格 / 代码质量；如需补充审查，提示 Boss 单独跑 `/code-review` |
| `code-self-check` | 本技能不审 diff 安全性；二者结果相互补充 |
| `unified-test` / `test-gen` | 本技能是其前置门禁；未通过不允许进入系统测试 |

## 禁止事项

1. 不要根据"测试通过率"代替"需求逐项验证"——测试可能没覆盖某个需求
2. 不要把"代码看起来对"当作通过依据——必须运行验证证据
3. 不要让实现者自审自验——本技能必须以独立第三方视角执行
4. 不要在矩阵缺失时凭直觉打分——直接 BLOCKED 回上游补矩阵
5. 不要把"越界实现"当成"做得多更好"——YAGNI / 铁律三违规一律阻断
