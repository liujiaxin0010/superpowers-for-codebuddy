# 执行计划

在门禁通过前，不允许进入执行阶段；在证据不完整前，不允许声称任务完成。

## 硬门禁前置条件

执行前先运行 `.codebuddy/skills/process-gatekeeper/SKILL.md`。

若被阻断：

- 输出阻断结果
- 不执行任何任务

## 阻断条件

以下任一情况直接返回 `BLOCKED`：

1. 缺少 spec、plan 或 TaskContract
2. 当前批次没有明确目标、验证命令或允许修改范围
3. 计划中的人工确认点尚未通过
4. 需要真实回滚、生产级变更或共享契约改动，但计划中没有对应保护措施

## 必备上下文

进入执行前，必须同时加载：

1. spec
2. plan
3. TaskContract / 合同摘要
4. 最近一次 `docs/progress.md`
5. 与当前批次相关的 `docs/findings.md`（如存在）

## 批次切分策略

不要把整份计划当成一个大批次直接推进。按以下规则切分：

1. **共享边界变更单独成批**：接口、数据模型、公共组件、共享配置变更必须单独批次
2. **高风险集成提前暴露**：跨模块接入、迁移、回滚准备要早于大面积实现
3. **同一验证命令可合并**：若多个任务共享同一模块和同一验证链路，可合并为一个批次
4. **出现人工确认点立即停批**：涉及方向确认、真实回滚、外部依赖接入时，不跨过确认点继续执行

## 执行工作流

### 1. 选定当前批次

明确当前批次的：

1. 目标
2. 允许修改范围
3. 验证命令
4. 完成定义
5. 回退方式

### 2. 按任务顺序执行

1. 按依赖顺序执行任务
2. 严格遵循 TDD：`RED -> GREEN -> REFACTOR`
3. 先完成当前批次，再进入下一批次
4. 任何超出合同范围的改动，先停下并记录，不得顺手扩展

### 3. 每项任务完成后做证据闭环

每项任务至少提供：

1. 修改文件或模块
2. 运行的验证命令
3. 验证结果
4. 是否存在剩余风险

没有证据，不算完成。

### 4. 批次完成后更新持久化文件

1. `docs/progress.md`：记录状态、完成项、下一步
2. `docs/findings.md`：只记录可复用结论、失败模式、技术判断

## 立即暂停条件

出现以下任一情况时，必须暂停当前批次：

1. 验证命令失败且根因不明
2. 实际影响面超出合同边界
3. 需要改动共享契约，但计划中未覆盖
4. 出现数据风险、权限风险、删除/迁移风险
5. 需要真实回滚或生产级破坏性操作

## 失败回退规则

1. 先保留证据：失败命令、错误信息、相关 diff
2. 更新 `docs/progress.md`，写明阻断点
3. 若批次内可安全回退，只做**回滚准备或 dry-run 演练**
4. 真实回滚前必须获得 Boss 的显式确认
5. 执行真实回滚前必须先记录快照点（commit/tag/备份点）与恢复命令

## 质量与收尾

完成前必须运行质量门禁脚本（`check-quality`），未通过不得收尾。

收尾输出必须声明：

1. 已完成的批次
2. 运行过的验证
3. 剩余风险
4. owner
5. handoff 建议

## 日志改动约束

涉及日志改动时必须：

1. 复用项目日志结构（或落实新项目已选框架）
2. 保持日志英文
3. 不使用控制台输出（除非用户明确要求）

## 分级策略

- L：标准执行并补齐测试
- M：完成前强制执行 `/code-review`
- H：必须具备头脑风暴证据，并设置风险/回滚检查点（默认 dry-run）

## 禁止事项

1. 不要跳过门禁直接执行
2. 不要把多个高风险任务混成一个大批次
3. 不要在验证失败后继续推进后续任务
4. 不要未更新 `progress/findings` 就声称批次完成
5. 不要默认执行真实回滚
