# 评分证据模式

本文件只在证据归类和保守评分时读取。

## 高可信证据

1. 用户明确说“能用 / 不能用”
2. 展示了测试通过或运行结果
3. 生成了明确的 spec / plan / report 文档

## 中可信证据

1. 展示了构建成功
2. 展示了代码改动，但没有运行验证
3. 展示了命令调用痕迹，但没有最终结果
4. 代码分析显示文件存在且有实际实现，但对话中无运行验证

## 低可信证据

1. 仅口头说”已完成”
2. 仅凭代码量大判断完成度
3. 仅凭调用了多个技能判断质量高
4. 代码分析仅发现骨架/空壳代码

## 代码分析证据（需启用 projectDir）

### 强化证据

- 对话声称完成 + 代码分析验证文件存在且有实现 → 增强为高可信
- 测试文件存在且有测试用例 → 增强测试通过证据的可信度

### 削弱证据

- 对话声称完成但代码分析显示文件不存在 → 降级为虚假完成（0 分）
- 对话声称完成但代码分析显示仅为空壳实现 → 降级为无证据（0 分）
- 项目缺少入口点或依赖声明 → 降低可运行性置信度

### 代码分析不能推翻的证据

- 用户明确报告失败 → 无论代码分析结果如何，始终为 0 分
- 用户明确确认功能正常 → 代码分析仅作为补充参考，不降低评分

## 保守评分原则

当证据冲突时：

1. 用户负反馈优先
2. 运行/测试证据优先于构建证据
3. 文档产物优先于口头承诺
4. 代码分析结果不能推翻用户明确反馈，但可推翻无运行验证的口头声称
