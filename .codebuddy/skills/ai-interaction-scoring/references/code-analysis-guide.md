# 代码分析指南

本文件在提供了 `projectDir` 参数时按需读取，用于指导代码分析的执行。

## 触发条件

仅当用户提供了 `projectDir` 参数（项目根目录路径）时，才执行代码分析。未提供时降级回纯对话评分模式。

## 分析步骤

### 第一步：项目类型识别

根据项目根目录中的特征文件自动判断项目类型：

| 特征文件 | 项目类型 | 语言/框架 |
|----------|----------|-----------|
| `package.json` | Node.js 项目 | JavaScript/TypeScript |
| `vite.config.*` / `vue.config.*` | Vue 项目 | Vue + Vite/Webpack |
| `next.config.*` | Next.js 项目 | React + Next.js |
| `go.mod` | Go 项目 | Go |
| `Cargo.toml` | Rust 项目 | Rust |
| `pom.xml` / `build.gradle` | Java 项目 | Java |
| `requirements.txt` / `pyproject.toml` / `setup.py` | Python 项目 | Python |

### 第二步：结构完整性检查

根据识别出的项目类型，检查是否具备该类型项目的标准目录结构。

#### Vue/前端项目

| 检查项 | 预期路径 | 权重 |
|--------|----------|------|
| 入口文件 | `src/main.ts` 或 `src/main.js` | 高 |
| 根组件 | `src/App.vue` | 高 |
| 路由配置 | `src/router/` | 中 |
| 状态管理 | `src/store/` 或 `src/stores/` | 中 |
| 页面组件 | `src/views/` 或 `src/pages/` | 高 |
| 公共组件 | `src/components/` | 中 |
| 构建配置 | `vite.config.*` 或 `webpack.config.*` | 高 |
| 依赖声明 | `package.json` | 高 |

#### Go 项目

| 检查项 | 预期路径 | 权重 |
|--------|----------|------|
| 模块声明 | `go.mod` | 高 |
| 主入口 | `main.go` 或 `cmd/*/main.go` | 高 |
| 业务逻辑 | `internal/` 或 `pkg/` | 中 |
| 配置文件 | `configs/` 或 `config/` | 低 |
| API 定义 | `api/` 或路由注册文件 | 中 |

#### Python 项目

| 检查项 | 预期路径 | 权重 |
|--------|----------|------|
| 依赖声明 | `requirements.txt` 或 `pyproject.toml` | 高 |
| 主入口 | `main.py` 或 `app.py` 或 `manage.py` | 高 |
| 包目录 | `src/` 或以项目名命名的目录（含 `__init__.py`） | 中 |
| 配置文件 | `config.py` 或 `.env` | 低 |

#### Java 项目

| 检查项 | 预期路径 | 权重 |
|--------|----------|------|
| 构建文件 | `pom.xml` 或 `build.gradle` | 高 |
| 主入口 | `*Application.java` 或含 `main()` 的类 | 高 |
| 源码目录 | `src/main/java/` | 高 |
| 资源目录 | `src/main/resources/` | 中 |
| 配置文件 | `application.yml` 或 `application.properties` | 中 |

### 第三步：核心代码验证

对对话中声称已完成的每个交付物，验证对应代码是否真实存在且非空壳。

#### 空壳代码识别规则

以下模式判定为"空壳实现"，不算真正完成：

1. **函数体仅含占位符**：`TODO`、`FIXME`、`pass`、`panic("not implemented")`、`throw new Error("not implemented")`、`// ...`
2. **文件仅有导入和空导出**：文件只声明了 import 和 export，无实际逻辑
3. **组件仅有模板骨架**：Vue/React 组件只有 `<template>` 和空 `<script>`，无实际交互逻辑
4. **接口定义无实现**：只有 interface/type 声明，无对应实现类或函数

#### 实现充分性判断

| 指标 | 判定为"有实际实现" | 判定为"空壳/骨架" |
|------|-------------------|-------------------|
| 函数体行数 | > 3 行有效代码（不含注释和空行） | <= 3 行或仅含占位符 |
| 组件逻辑 | 有事件处理、数据绑定、计算属性等 | 仅有静态模板 |
| API 处理器 | 有请求解析、业务逻辑、响应返回 | 仅返回固定值或 TODO |
| 数据操作 | 有 CRUD 操作的实际实现 | 仅有空方法签名 |

### 第四步：测试覆盖检查

检查测试文件是否存在及测试用例数量。

| 语言/框架 | 测试文件模式 | 测试用例识别 |
|-----------|-------------|-------------|
| JavaScript/TypeScript | `*.test.ts`、`*.spec.ts`、`__tests__/` | `it(`、`test(`、`describe(` |
| Vue | `*.spec.ts`、`*.test.ts` | `it(`、`test(` |
| Go | `*_test.go` | `func Test`、`func Benchmark` |
| Python | `test_*.py`、`*_test.py`、`tests/` | `def test_`、`class Test` |
| Java | `*Test.java`、`*Tests.java`、`src/test/` | `@Test`、`@ParameterizedTest` |

### 第五步：依赖与构建可行性

1. **依赖声明是否存在**：`package.json`、`go.mod`、`requirements.txt`、`pom.xml` 等
2. **依赖声明是否合理**：不为空、包含项目实际使用的核心库
3. **构建/启动入口是否存在**：`main` 入口文件、`scripts.start`/`scripts.dev` 等
4. **构建配置是否存在**：Makefile、Dockerfile、CI 配置等（可选加分项）

## 交叉验证规则

代码分析结果与对话证据结合，按以下规则确定最终证据级别：

| 对话证据 | 代码分析结果 | 最终判定 | 说明 |
|----------|-------------|----------|------|
| 声称完成 + 运行验证 | 代码存在且有实现 | 完整证据（2 分） | 最强证据组合 |
| 声称完成 + 运行验证 | 代码不存在 | 部分证据（1 分） | 可能代码在分析路径之外，标记需人工确认 |
| 声称完成，无运行验证 | 代码存在且有实现 | 部分证据（1 分） | 代码存在但未验证运行 |
| 声称完成，无运行验证 | 代码为空壳 | 无证据（0 分） | 标记"虚假完成" |
| 声称完成，无运行验证 | 代码不存在 | 无证据（0 分） | 标记"虚假完成" |
| 无明确声明 | 代码存在且有实现 | 部分证据（1 分） | 代码存在但对话未确认 |
| 无明确声明 | 代码不存在 | 无证据（0 分） | — |
| 用户报告失败 | 任意 | 无证据（0 分） | 用户反馈优先级最高 |

## 代码分析报告输出字段

对每个交付物，代码分析输出以下字段：

```
交付物名称:
  文件存在: 是/否（列出匹配的文件路径）
  实现充分性: 完整实现/骨架代码/空壳/不存在
  测试覆盖: 有测试文件（N个用例）/无测试文件
  对话证据: 声称完成/用户确认/用户报告失败/无明确声明
  交叉判定: 完整证据/部分证据/无证据
  最终得分: 0/1/2
```

## 禁止事项

1. 不要因为文件数量多就判定完成度高——空壳文件不算完成
2. 不要在代码分析结果与用户明确反馈冲突时，以代码分析为准——用户反馈始终优先
3. 不要对不在 `projectDir` 内的文件做分析推断
4. 不要执行项目代码或运行构建命令——仅做静态文件检查
