# AI 交互质量评分

## 输入参数

`/score-interaction <对话内容> [name=<姓名>] [id=<工号>] [task=<需求名称>] [projectDir=<项目路径>] [outputDir=<输出路径>]`

| 参数 | 必填 | 默认值 | 说明 |
|------|------|--------|------|
| conversation | 是 | - | 对话内容（文本/JSON）或文件路径 |
| name | 是 | - | 被评人姓名，用于报告文件命名 |
| id | 是 | - | 被评人工号，用于报告文件命名 |
| task | 是 | - | 需求名称，用于评分基线和文件命名 |
| projectDir | 否 | - | 项目根目录路径，提供时启用代码分析增强评分 |
| outputDir | 否 | `docs/scoring/` | 报告输出目录 |

## 输出文件命名规则

报告文件名格式：`{姓名}_{工号}_{需求名称}.md` / `{姓名}_{工号}_{需求名称}.xlsx`

示例：
- `张三_10086_文件映射服务.md`
- `张三_10086_文件映射服务.xlsx`

如果参数缺失，必须在评分前向用户询问姓名、工号和需求名称。

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 没有提供可分析的对话内容
2. 缺少 `name`、`id`、`task` 且用户也未补充
3. 输入内容不足以支撑四个维度中的任何一个维度判断

## 资源加载约束

1. 不要一开始就把模板和规则文件都全量展开后再分析对话——先做证据抽取，再按需加载
2. 不要在未提供 `projectDir` 时加载代码分析指南

## 何时使用

1. 用户要求对一段 AI 对话进行质量评分或绩效评估
2. 用户显式调用 `/score-interaction` 并提供对话内容
3. 需要生成结构化的 AI 编码助手交付质量报告

## 何时不用

1. 用户只是想回顾对话内容，不需要打分
2. 对话内容不涉及编码任务（纯聊天、纯问答）
3. 用户要求的是代码审查而非交互质量评分——应使用 `requesting-code-review`

## 评分维度（总分：30 分）

### 维度一：Spec-Coding 规范（10 分）

评估对话是否在编码前遵循了结构化的规格优先方法。

| 得分 | 证据标准 |
|------|----------|
| 0 | 一开始就直接编码，无任何规划讨论 |
| 3 | 有简单的需求描述但无结构化文档 |
| 5 | 部分规格：有需求分析或接口设计，但不完整 |
| 7 | 有需求分析 + 接口设计 + 技术方向，但缺少正式的规格文档 |
| 10 | 完整的 spec-coding 流程：需求澄清 + 方向评估 + 正式规格文档 + 实施计划 |

**检测模式：**

1. Spec 相关关键词：`spec`、`plan`、`设计`、`接口定义`、`数据结构`、`技术方案`、`API 设计`
2. Spec 相关命令：`/spec-lite`、`/write-plan`、`/brainstorm`、`/Featureflow`、`/research`
3. Spec 文档产物：`docs/specs/`、`docs/plans/`、`spec/` 目录下的文件
4. 需求澄清证据：编码前的多轮问答
5. 方向评估证据：对比多个实现方案及权衡分析
6. 计划文档产物：包含批次/阶段的任务分解

**评分细则：**

- +2：存在需求澄清阶段（多轮问答）
- +2：技术方向评估，提供多个方案选项
- +2：生成正式规格文档（spec-lite 或等效文档）
- +2：包含任务分解和批次的实施计划
- +1：维护了持久化文档（findings.md、progress.md）
- +1：引用了门禁检查或质量关卡

### 维度二：Skills/Agent 使用（5 分）

评估对话中技能和 Agent 的使用广度。

| 得分 | 证据标准 |
|------|----------|
| 0 | 未使用任何 `/` 命令或 Agent |
| 2 | 使用了 1 个技能或 Agent |
| 3 | 使用了 2 个技能或 Agent |
| 4 | 使用了 3 个技能或 Agent |
| 5 | 使用了 4 个及以上不同的技能或 Agent |

**检测方法：**

1. 统计对话中不同 `/xxx` 斜杠命令的调用次数
2. 检测 Agent 调用（code-reviewer、task-implementer 等）
3. 参考 `.codebuddy/commands/` 和 `.codebuddy/skills/` 中的技能列表
4. 常见技能：`/Featureflow`、`/spec-lite`、`/write-plan`、`/execute-plan`、`/code-review`、`/unified-test`、`/test-gen`、`/fix-bug`、`/simplify`、`/brainstorm`、`/extend`、`/research`、`/status`、`/doc-sync`、`/pua`
5. 去重：同一技能多次调用计为 1 次

### 维度三：项目完成度（10 分）

评估交付的项目是否实际可运行，当无法直接执行时使用代理指标。

**评估与任务相关。** 评分系统根据实际任务需求进行调整。针对每个任务识别 5 个核心交付物，每个 2 分。

**通用交付物评估模板（每项 2 分）：**

| 评估项 | 证据来源 |
|--------|----------|
| 核心功能 1 | API 端点 + 处理器代码 + 前端集成 |
| 核心功能 2 | API 端点 + 处理器代码 + 前端集成 |
| 核心功能 3 | API 端点 + 处理器代码 + 前端集成 |
| 核心功能 4 | API 端点 + 处理器代码 + 前端集成 |
| UI/UX 完整性 | UI 框架 + 布局组件 + 结构化样式 |

**每个交付物按以下标准评分：**

| 证据级别 | 分值 | 标准 |
|----------|------|------|
| 完整证据 | 2 | 代码存在 + 测试通过 + 运行时验证展示 |
| 部分证据 | 1 | 代码存在 + 编译/构建成功，但无运行时验证 |
| 无证据 | 0 | 代码缺失或损坏，无编译证据 |

**补充证据（增强或削弱评分）：**

- 启动命令（`npm start`、`go run` 等）及成功输出日志
- 测试执行记录及通过/失败结果
- 截图或 `localhost:xxx` 访问描述
- 用户确认功能正常
- 用户报告 Bug 或故障（负面证据）

**核心规则：** 如果用户明确报告某功能不可用（如"页面上没有文件"），该功能无论代码是否存在，一律评 0 分。

#### 代码分析增强（可选）

当提供了 `projectDir` 参数时，在对话证据基础上叠加代码分析，提升评分准确性。

**分析内容：**

1. **文件存在性**：对话中声称的文件/模块是否在项目中真实存在
2. **结构完整性**：项目是否具备该类型项目的标准目录结构（如 Vue 项目需有 src/main.ts、src/App.vue 等）
3. **实现充分性**：关键函数/组件/API 是否有实际实现，而非 TODO/pass 等空壳
4. **测试覆盖**：测试文件是否存在、测试用例数量是否合理
5. **依赖完整性**：package.json/go.mod 等依赖文件是否存在且合理
6. **构建可行性**：是否存在构建/启动配置和入口点

**交叉验证规则：**

| 对话证据 | 代码分析结果 | 最终判定 |
|----------|-------------|----------|
| 声称完成 + 运行验证 | 代码存在且有实现 | 完整证据（2 分） |
| 声称完成 + 运行验证 | 代码不存在 | 部分证据（1 分），标记需人工确认 |
| 声称完成，无运行验证 | 代码存在且有实现 | 部分证据（1 分） |
| 声称完成，无运行验证 | 代码为空壳或不存在 | 无证据（0 分），标记虚假完成 |
| 无明确声明 | 代码存在且有实现 | 部分证据（1 分） |
| 用户报告失败 | 任意 | 无证据（0 分） |

**未提供 `projectDir` 时：** 降级回纯对话证据评分，行为与原有逻辑完全一致。

详细的分析步骤和各语言项目特征见 `references/code-analysis-guide.md`。

### 维度四：扩展功能与界面美化（5 分）

评估项目是否超越了基本需求。

| 得分 | 证据标准 |
|------|----------|
| 0 | 仅完成基本需求，无额外功能 |
| 2 | 有扩展功能或界面美化（二者之一） |
| 3 | 两者兼具，但存在已知 Bug 或实现不完整 |
| 4 | 两者兼具，大部分功能正常 |
| 5 | 两者兼具，且经验证可正常工作 |

**扩展功能关键词：**

- 分类/标签、优先级、搜索/筛选、拖拽排序
- 完成统计、本地存储/localStorage、深色模式
- 文件预览、批量操作、实时同步、通知
- 分页、导出、导入、快捷键

**界面美化关键词：**

- 响应式设计、动画/过渡效果、主题/深色模式
- 图标/图标库、移动端适配/媒体查询
- UI 组件库（Ant Design、Element Plus、Naive UI 等）
- 布局组件、栅格系统、卡片/面板设计

## 执行流程

1. **解析输入**：提取对话内容和可选参数（含 `projectDir`）
2. **任务识别**：确定任务类型和核心交付物
3. **证据收集**：在 4 个维度中扫描对话证据。**若遇到"某段证据该不该算分、该按完整还是部分计"的模糊判断，此时读取 `references/evidence-patterns.md`**
4. **代码分析**（可选）：仅当提供了 `projectDir` 时，**读取 `references/code-analysis-guide.md`**，对每个交付物执行文件存在性、实现充分性、测试覆盖等检查
5. **交叉验证**（可选）：将代码分析结果与对话证据交叉比对，按规则确定最终证据级别
6. **分数计算**：按评分规则映射证据并计算得分。**此时读取 `scoring-rules.json` 获取精确的维度映射和分值规则**
7. **亮点分析**：识别优势和不足
8. **报告生成**：**读取 `templates/score-report-template.md`**，按模板结构输出 MD 报告 + XLSX 汇总表

## 证据抽取顺序

优先按以下顺序取证：

1. 用户明确陈述
2. 命令调用与文档产物
3. 测试/构建/运行证据
4. 代码分析结果（仅在提供 `projectDir` 时可用）
5. 代码改动痕迹（对话中提到的代码变更）

若高层证据和低层证据冲突，以更直接、更贴近结果的证据为准。

## 评分约束

1. 评分基于**对话中的证据**，而非猜测
2. 当证据模糊时，采用保守评分
3. 用户明确报告功能不可用时，优先视为负面证据
4. 编译成功不等于功能可用

## 输出产物

### 主报告：`{姓名}_{工号}_{需求名称}.md`

在 `outputDir` 目录下使用 `templates/score-report-template.md` 模板生成。

### 汇总表：`{姓名}_{工号}_{需求名称}.xlsx`

使用 `xlsx` 技能生成。列定义、列宽和条件着色格式见 `scoring-rules.json` 的 `outputConfig.xlsxColumns` 和 `outputConfig.xlsxFormatting` 字段——**生成 XLSX 前必须读取该配置**。

## 反模式检测

评分系统应标记以下负面模式：

| 反模式 | 影响 | 检测方式 |
|--------|------|----------|
| 虚假完成 | 维度三扣分 | 声称"已完成"但未运行测试验证 |
| 过早编码 | 维度一扣分 | 跳过规划直接编码 |
| Bug 修复循环 | 维度三扣分 | 同一 Bug 修复 3 次以上仍未解决 |
| 范围蔓延 | 在报告中标注 | 显著的功能增加不在原始 spec 范围内 |
| 忽略用户反馈 | 维度三扣分 | 用户报告问题，AI 未解决或无证据地声称已修复 |
| 代码虚报 | 维度三扣分 | 对话声称完成但代码分析显示文件不存在或仅为空壳（需启用代码分析） |

## 评分校准说明

- 评分基于**对话中的证据**，而非假设
- 当证据模糊时，采用保守评分（偏低）
- 用户关于功能的陈述优先于代码分析（用户说"不能用" = 不能用）
- 编译成功不足以作为"功能正常"的充分证据
- 各维度独立评分；某一维度的高分不能弥补另一维度的低分

## 禁止事项

1. 不要因为代码“看起来不少”就给高完成度
2. 不要把命令调用次数直接等同于质量
3. 不要在缺少核心参数时硬生成最终报告
4. 不要忽视用户负反馈
5. 不要把模板内容当作评分证据本身
