# 分支场景矩阵

本文件只在默认决策不够用时读取。若当前是“Git + 干净目录 + 单任务 + 默认从 main 切出”，不需要加载本文件。

## 快速决策表

| 场景 | 推荐策略 | 原因 |
|---|---|---|
| Git + 当前目录干净 + 单任务 | 普通分支 | 最低成本、上下文简单 |
| Git + 当前目录已有未提交改动 | 切到 `using-git-worktrees` | 避免污染已有改动 |
| Git + 需要并行推进多个任务 | 切到 `using-git-worktrees` | 分离上下文与验证链路 |
| Git + hotfix / release 维护 | 从对应 release/hotfix 分支切出 | 避免把维护任务绑到 main |
| Git + 任务明确依赖未发布分支 | 从该基线分支切出，并说明原因 | 保持上下游一致 |
| SVN | 使用标准 SVN 分支流程 | 与 Git 规则分离 |
| 无法识别 VCS | `BLOCKED` | 不能盲切 |

## dirty worktree

出现以下任一情况时，不要在当前目录直接新开普通分支：

1. 已有未解释的本地改动
2. 用户正在另一个任务上工作
3. 当前目录本身就是脏工作区的临时落点

默认动作：

1. 切到 `using-git-worktrees`
2. 或先由用户确认如何处理现有改动

## release / hotfix / 维护分支

只有以下理由之一成立，才从非 `main` 基线切出：

1. 当前任务就是维护已发布版本
2. Bug 只存在于某条 release 线
3. 新功能明确依赖未发布基线

如果说不清为什么不从 `main` 切，默认回到 `main`。

## 命名规则

推荐命名：

1. `feature/<目标>`
2. `fix/<问题>`
3. `refactor/<范围>`
4. `chore/<事项>`

命名必须至少回答两个问题：

1. 这是功能、修复还是重构
2. 它对应哪个任务或需求

无效命名示例：

1. `test1`
2. `tmp`
3. `new-branch`

## 何时必须记录决策

出现以下任一情况时，使用模板记录：

1. 不是从默认基线切出
2. 选择了 worktree 而不是普通分支
3. 分支命名带有维护线、发布线或多任务上下文
4. 需要向 Boss / owner 解释为什么这么切
