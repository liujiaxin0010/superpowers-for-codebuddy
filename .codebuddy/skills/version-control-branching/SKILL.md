# 版本控制分支管理

本技能回答的是：**当前任务该用什么隔离策略、从哪条基线切出、分支该怎么命名。**

## 核心心智：基线决定上限

分支的质量上限由它的基线决定。从一个测试已经失败的基线切出，后续所有开发都无法区分"新引入的问题"和"基线遗留的问题"。从错误的基线切出（如从旧 release 而非 main），会引入已修复的 bug 或缺少必要的上游依赖。

因此：**先验证基线，再创建分支。**

## 分支命名约定

| 任务类型 | 命名模式 | 示例 |
|---|---|---|
| 新功能 | `feature/<简短描述>` | `feature/user-auth` |
| Bug 修复 | `fix/<issue-id>-<描述>` | `fix/1234-login-crash` |
| 重构 | `refactor/<描述>` | `refactor/extract-service` |
| Hotfix | `hotfix/<version>-<描述>` | `hotfix/v2.1-payment-fix` |
| 实验 | `experiment/<描述>` | `experiment/new-cache-strategy` |

命名必须能让不知道上下文的人从名称推断出任务类型和目标。

## 资源加载规则

当遇到 dirty worktree、并行任务、release/hotfix 维护、非默认基线或默认判断不够用时，再读取：

- `references/branch-scenario-matrix.md`

当不是“Git + 干净目录 + 单任务 + 默认从 main 切出”的简单场景时，再读取：

- `templates/branch-decision-template.md`

如果默认决策已经足够清楚，不要提前加载模板。

## 何时使用

1. 需求已被批准，准备进入实现
2. 需要为新功能、bug 修复或重构建立隔离开发空间
3. 需要决定是普通分支、worktree 还是 SVN 分支

## 何时不用

1. 只是临时切换目录看代码，并不进入实现
2. 已经处在正确的隔离工作树或维护分支中
3. 任务本质是并行调度或 worktree 管理，应交给 `dispatching-parallel-agents` 或 `using-git-worktrees`

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 无法识别 `.git` 或 `.svn`
2. 目标基线分支不明确
3. 当前目录存在未解释的本地改动，且用户未说明如何处理
4. 基线测试已失败，无法确认干净起点

## 选择协议

1. 先识别 VCS：Git、SVN，无法识别就阻断
2. 再选隔离策略：dirty worktree、多任务并行默认切到 `using-git-worktrees`
3. 再选基线：默认 Git 从 `main`，SVN 从 `trunk`
4. 只有在维护 release/hotfix 或依赖未发布基线时，才从非默认基线切出
5. 最后确定分支命名，名称必须体现任务类型与目标

## 基线检查

开始前至少确认：

1. 当前依赖可安装或已安装完成
2. 现有测试至少主路径可运行
3. 本地状态干净，或已明确采用 worktree 隔离
4. 基线分支与后续验证命令已明确

## 与 worktree 的关系

以下情况不要在本技能里继续展开普通分支操作，直接切到 `using-git-worktrees`：

1. 当前目录已有未提交改动
2. 需要并行推进多个任务
3. 需要隔离 agent 或多人的工作目录

## 输出要求

1. 说明 VCS 类型
2. 说明隔离策略：普通分支 / worktree / SVN 分支
3. 说明基线分支或路径
4. 说明新分支命名
5. 若不是默认决策，说明原因并套用模板

## 禁止事项

1. 不要在脏工作目录里默认新开普通分支——未提交的改动会被带入新分支，污染基线并导致 diff 混乱
2. 不要在基线测试未确认前进入实现——在已经失败的基线上开发会导致无法区分新引入问题和遗留问题
3. 不要把 worktree 适用场景硬塞回普通分支——频繁切换分支会丢失构建缓存、IDE 索引，且未提交改动会互相干扰
4. 不要使用 `test1`、`tmp`、`new-branch` 这类无语义命名——无语义分支名在多人协作和历史回溯时完全无法识别用途
5. 不要在说不清原因时从非默认基线切出——错误的基线会引入未预期的依赖或缺失必要的上游变更
