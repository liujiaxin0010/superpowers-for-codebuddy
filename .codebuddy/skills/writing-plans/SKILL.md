# 编写计划

将已确认设计转换为**可执行、可验证、可交接**的任务计划。写计划前必须先通过门禁检查。

## 硬门禁前置条件

先运行 `.codebuddy/skills/process-gatekeeper/SKILL.md`。

若 `GateResult.status=blocked`：

- 输出阻断结果
- 立即停止

## 输出路径

`docs/plans/YYYY-MM-DD-<feature>.md`

## 计划中必填元数据

```yaml
specPath: docs/specs/...
taskType: new-feature|bugfix|refactor|test|research|review-pr|issue-draft-pr|parallel-delivery
finalTier: L|M|H
gateStatus: pass
```

## 何时不用

1. 需求尚未完成规格澄清——应先使用 `/spec-lite`
2. 任务是简单 bugfix（L 级、<=2 文件）且修复路径明确——可直接修复
3. 用户只需要研究或调研，不涉及实施交付——应使用 `/research`
4. 已有可用的计划文档且需求未变更——不需要重复编写

## 阻断条件

若以下任一项不满足，直接返回 `BLOCKED`，不得继续拆解：

1. spec 的“需求澄清结论”已完成
2. spec 的“方案方向确认”已完成
3. 不存在 `TBD/待定/未确认`
4. 若用户否决候选方向，已记录明确替代方向与硬约束
5. TaskContract 已补齐目标、允许修改、禁止修改、验证命令、交付证据、人工确认点、owner

## 拆解原则

1. 每个任务都必须对应一个**可验证结果**，不要只写模糊动作
2. 任务粒度默认控制在 2-5 分钟，但不能牺牲验证闭环
3. 优先按边界、接口、风险和验证链路拆解，不按”文件越多越细”机械切分
4. 计划必须能直接支撑执行，不允许出现大量 `TBD/待定/后面再看`

**开始拆解时，必须先读取 `references/decomposition-guide.md`**，对照拆解决策矩阵和启发式规则逐项检查后再输出任务列表。

## 每个任务必须写清的字段

1. 任务目标
2. 允许修改
3. 禁止修改
4. 验证命令
5. 交付证据
6. 人工确认点（如有）
7. 依赖项

## 计划质量检查

成稿前，至少逐条自检：

1. 有没有任务缺少验证命令
2. 有没有“实现”和“验证”被割裂到完全无关的两步
3. 有没有并行任务实际上共享核心文件
4. 有没有遗漏代码审查、文档同步、回归验证
5. 有没有把高风险共享修改伪装成普通任务

## 必备章节

1. 风险缓解章节
2. 合同摘要：目标、允许修改、禁止修改、验证命令、交付证据、人工确认点、owner
3. 日志相关改动与验证：
   - 旧项目：复用原有日志结构
   - 新项目：落实已选日志框架与字段规范
   - 验证无中文日志、无控制台输出残留（除非用户要求）

## 分级附加要求

- L：最小可执行任务链
- M：补充明确风险缓解任务，并强制代码审查阶段
- H：必须具备头脑风暴证据，并包含“回滚准备 + dry-run 演练”任务

## 回滚任务编排约束（默认安全模式）

**H 级计划包含回滚任务时，必须读取 `references/rollback-constraints.md`**，按其中的两步拆分规则编排回滚任务。

## 反模式

1. 不要写成”改代码 / 联调 / 测一下”这类不可验证任务——无法验证的任务无法判断完成状态，执行者会陷入无限循环
2. 不要把实现和验证拆到毫无关系的两个任务里——割裂实现与验证会导致验证覆盖不到实际变更点
3. 不要把共享边界改动和多个消费方修改混成同一任务——混合任务一旦失败无法回滚单个变更，影响范围不可控
4. 不要把并行任务建立在隐含依赖之上——隐含依赖会在并行执行时产生竞态条件，导致不可复现的集成失败
5. 不要遗漏代码审查、文档同步、回归验证等收尾任务——缺少收尾任务的计划会在交付时产生”最后一公里”阻塞
6. 不要让计划在阅读后仍无法判断”先做什么、后做什么、如何验收”——不可执行的计划等于没有计划，执行者会自行决策导致偏移
