# 代码简化

本技能回答的是：**这段代码值不值得动，应该先动哪类坏味道，怎样在不改行为的前提下收口。**

## 资源加载规则

当需要判断“重复逻辑 / 深层嵌套 / 超长函数 / 命名含糊 / 低价值手写实现”该怎么下手时，再读取：

- `references/simplification-patterns.md`

当已经决定动手，需要输出“行为不变”的证据闭环时，再读取：

- `templates/simplification-evidence-template.md`

不要一开始就同时加载 reference 和 template；先判断值不值得动，再按需读取。

## 何时使用

1. Boss 明确要求简化代码
2. 长时间编码后准备收尾
3. PR 前要做最后一轮清理
4. 某段代码明显复杂、重复、难读，但业务行为已基本稳定

## 何时不用

1. 目标其实是新增功能、架构迁移或跨模块重构
2. 当前区域行为尚不稳定，仍在频繁试错
3. 问题本质是 bug 修复、公共契约调整或排查未知行为

## 前置条件

1. 现有测试足够覆盖行为
2. 可以先补最小行为验证
3. 改动范围已被 Boss 明确限定

若行为尚不清楚、测试缺失且无法补最小验证，不要贸然简化。

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 无法确认当前行为，也无法建立最小验证
2. 继续简化必须修改公共 API 或跨模块契约
3. 用户要求的是重构或新增功能，而不是“保持行为不变的简化”

## 核心约束

1. 保持功能不变，只改实现方式
2. 不引入新依赖，除非 Boss 明确要求
3. 不跨模块大重构，除非 Boss 明确授权
4. 可读性优先于“更少行数”
5. 每轮简化后都要重新验证

## 决策协议

1. 先确认收益门槛：至少带来“降低认知负担 / 减少重复 / 降低嵌套层级 / 让验证更容易”中的一项
2. 再选最低风险入口：高频阅读痛点 > 明显重复 > 明显嵌套/超长函数 > 中风险高收益项
3. 若同一轮有多个简化点，只先动 1-3 个最值当的点
4. 若需要跨模块联动、修改公共 API 或靠猜测验证，直接停手

## 执行流程

1. 确定简化范围与明确不触碰的边界
2. 跑基线验证，确认当前行为稳定
3. 按需读取对应坏味道章节
4. 从最低风险项开始逐步简化
5. 每步后都跑验证
6. 套用证据模板输出“去掉了什么复杂度、保留了什么行为、用什么证据证明没变”

## 停止条件

出现以下任一情况时，停止继续简化：

1. 需要改公共 API 才能继续
2. 测试开始无法证明行为一致
3. 简化收益已经很低，只是在追求”更短”
4. 开始引入更高抽象成本或更强耦合

### 量化参考阈值

- 函数超过 50 行或嵌套超过 4 层：值得拆分
- 同一逻辑片段出现 3 次以上：值得提取
- 圈复杂度 > 10：优先降低
- 同一逻辑片段只出现 2 次且不超过 5 行：不值得提取，重复比过早抽象好

## 常见反模式

1. **为了短而短**：行数少了，但语义更晦涩
2. **过度抽象**：只为两处重复就引入接口、继承层或复杂模板
3. **顺手重构**：本来只想简化一个函数，最后改了半个模块
4. **删看似没用的代码**：没有证据就删除，容易破坏隐含依赖
5. **改错误处理策略**：这不是简化，这是行为变更
6. **把命名优化伪装成架构重构**：借简化之名扩大改动面

## 禁止事项

1. 不要改变公共 API 签名
2. 不要删除“看起来没用”的逻辑而不验证
3. 不要把简化扩展成跨模块重构
4. 不要在未跑验证时宣称“行为不变”
5. 不要用更炫的语法替代更清晰的写法
6. 不要忽略 reference 里的停手信号
