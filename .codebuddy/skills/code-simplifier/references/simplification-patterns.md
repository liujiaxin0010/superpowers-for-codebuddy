# 简化模式参考

本文件只在已经决定做代码简化后读取。按当前坏味道选择对应章节，不要整份通读。

## 重复逻辑

适用信号：

1. 相同业务判断在多个分支重复出现
2. 相同的后处理、校验、映射逻辑被复制
3. 多处代码只是常量、字段名或错误文案略有差异

优先动作：

1. 先提取共享表达式、共享校验或共享后处理
2. 若语言/标准库已有等价能力，优先复用标准库
3. 保留调用点的业务语义，不要把调用点意图一并抽空

风险边界：

1. 若重复代码在日志、监控、事务边界、错误文案上存在细微差异，不要盲目合并
2. 若两个分支依赖不同的空值、顺序、幂等或时序语义，先补验证再抽取

停手信号：

1. 提取后需要塞进多个布尔参数才能复用
2. 为了两处重复引入新的抽象层、接口层或继承层

## 深层嵌套

适用信号：

1. 条件嵌套超过 3 层
2. 主要业务路径被异常分支包住
3. 同一个缩进层级里既处理前置校验又处理核心逻辑

优先动作：

1. 先把失败分支改成卫语句或提前返回
2. 把明显独立的前置检查与核心路径拆开
3. 让主流程从“左对齐”开始，而不是继续堆缩进

风险边界：

1. 若嵌套中带有资源释放、锁、事务、状态恢复，不要为了拍平而破坏清理对称性
2. 若异常上下文依赖当前嵌套顺序，不要先改结构再找证据

停手信号：

1. 提前返回导致清理逻辑重复散落
2. 拍平后主流程更难看懂，或失去关键审计日志

## 超长函数

适用信号：

1. 单个函数同时承担解析、校验、转换、持久化等多个阶段
2. 阅读时必须在函数头尾来回跳转才能理解主线
3. 单测很难只覆盖其中一段职责

优先动作：

1. 按阶段或职责拆，不按行数硬切
2. 优先抽取“输入稳定、输出明确”的阶段
3. 把编排留在主函数，把细节下沉到辅助函数

风险边界：

1. 若抽取后需要传一长串参数或共享可变状态，说明边界切错了
2. 若抽取改变了事务、锁或错误处理边界，先停手

停手信号：

1. 新 helper 的命名和调用关系比原函数更难追
2. 抽出来的函数只是把控制流藏起来，没有降低理解成本

## 命名含糊

适用信号：

1. 变量/函数名看不出领域含义、单位、真假极性或返回约定
2. 代码读者必须靠上下文猜“这个值到底是什么”
3. 多个近义名称混用，导致同一概念在不同地方叫不同名字

优先动作：

1. 先改最近作用域里的命名，再考虑扩散范围
2. 优先澄清单位、状态、方向、真假语义
3. 能只做 rename 的，就不要和逻辑改动混成一个 patch

风险边界：

1. 公共 API、序列化字段、配置键、日志字段、监控指标名都可能是契约
2. 跨模块 rename 可能触发运行时绑定、脚本依赖或 grep 工作流断裂

停手信号：

1. rename 已经超出当前模块可控范围
2. 需要用户或 owner 确认对外命名契约时

## 低价值手写实现

适用信号：

1. 手写循环、拼接、去重、解析、排序逻辑其实标准库已有稳定实现
2. 代码的价值不在算法本身，而在业务规则
3. 手写实现增加了维护负担，却没有明显业务收益

优先动作：

1. 优先替换成语言或标准库自带能力
2. 替换前核对顺序、大小写、时区、舍入、Unicode、错误处理等语义
3. 若原实现承载业务怪癖，先把怪癖写成验证再替换

风险边界：

1. 不要为了“更现代”引入陌生语法糖，导致团队读不懂
2. 不要把“标准库替换”偷换成“新增第三方依赖”

停手信号：

1. 标准库方案和现有语义并不等价
2. 替换后反而隐藏了业务意图或增加了调试成本
