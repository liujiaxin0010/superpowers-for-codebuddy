# 子代理驱动开发

`Featureflow` 的核心创新之一。每个任务派遣一个**全新子代理**执行，随后通过**规格符合性审查 + 代码质量审查**形成制度化的不信任闭环。

## 何时使用

以下情况优先使用本技能：

1. 实施计划包含 3 个以上任务
2. 任务之间依赖关系清晰
3. 每个任务都能定义允许修改范围和验证命令
4. 需要长时间自主推进，但不希望上下文持续污染

## 何时不用

以下情况优先考虑 `executing-plans`：

1. Boss 需要在每批任务后手动审查
2. 任务之间依赖复杂，需要人工判断执行顺序
3. 项目风险过高，不适合自动连续推进

## 核心约束

1. 每个任务必须使用**全新上下文**的子代理
2. 未经过两阶段审查的任务，不得标记完成
3. 子代理只能在合同和计划边界内工作
4. 所有任务状态都必须同步到 `docs/progress.md`

## 模板加载规则

### 分发实现任务前

在创建 implementer 子代理前，**必须完整读取**：

- `templates/implementer-prompt.md`

### 进行第一阶段审查前

在创建 spec-reviewer 子代理前，**必须完整读取**：

- `templates/spec-reviewer-prompt.md`

### 进行第二阶段审查前

在创建 code-reviewer 子代理前，**必须完整读取**：

- `templates/code-reviewer-prompt.md`

### 不要怎么加载

1. 不要在实现任务前把三个模板全部一起塞进上下文
2. 不要口头描述模板意图却不真正读取模板文件

## 高层工作流

1. 读取计划、合同和当前进度
2. 为当前任务创建 implementer 子代理
3. implementer 完成任务并提交结果
4. 创建 spec-reviewer 做第一阶段审查
5. 通过后创建 code-reviewer 做第二阶段审查
6. 审查通过则标记完成；否则退回 implementer 修复
7. 所有任务完成后做一次全局代码审查

## 任务分发协议

每次分发 implementer 时，至少提供：

1. 任务编号与标题
2. 允许修改的文件或目录
3. 详细要求
4. 验证命令
5. 约束：TDD、YAGNI、禁止兼容性代码、文档同步
6. 相关上下文：GitNexus 结果或相关 `CONTEXT.md`

## 审查协议

### 第一阶段：规格符合性审查

关注：

1. 是否精确匹配规格
2. 是否遗漏功能点
3. 是否超出规格边界
4. 测试是否覆盖规格要求
5. 是否引入兼容性代码

### 第二阶段：代码质量审查

关注：

1. 正确性与安全性
2. 可维护性与耦合度
3. 测试质量
4. 文档同步

## 问题处理

1. `spec-reviewer` 或 `code-reviewer` 发现阻断问题：退回 implementer 修复
2. 严重问题未解决前，不得进入下一个任务
3. 审查分歧无法裁定时，升级给 Boss

## 进度与持久化

每个任务完成后必须：

1. 更新 `docs/progress.md`
2. 记录完成状态、修改文件、审查结果
3. 如有可复用结论，更新 `docs/findings.md`

## 全局审查

所有任务完成后，必须做一次全局审查：

1. 把所有任务的改动作为整体审视
2. 检查集成边界
3. 运行完整测试套件
4. 确认三层文档同步

## 禁止事项

1. 不要让同一个子代理连续执行多个任务
2. 不要跳过 `spec-reviewer` 或 `code-reviewer`
3. 不要在审查失败后直接标记完成
4. 不要分发超出合同边界的任务
5. 不要只靠 implementer 的自述判断任务是否完成
