# 完成开发分支

当实现已完成、局部验证已通过时，统一做一次**可交付前的收尾检查**，而不是边做边口头宣布”差不多了”。

## 核心心智：收尾 ≠ “差不多了”

收尾是一个独立的质量阶段，不是实现的尾声。常见的失败模式是开发者在实现最后一步时顺手说”搞定了”，但实际上：
- 调试代码还在（`console.log`、`print`、`TODO`）
- 本地有未提交的改动（忘了 `git add` 的新文件）
- 子代理各自通过但集成后有回归
- PR 描述是空的或复制粘贴

收尾的价值在于**用清单替代记忆**——人脑在完成核心任务后注意力会下降，清单式检查能捕获遗漏。

## 资源加载规则

当需要逐项执行收尾检查、worktree 清理或路径切换前的总清单时，再读取：

- `references/branch-exit-checklist.md`

当收尾路径是 `A: 创建 PR/MR` 时，再读取：

- `templates/pr-summary-template.md`

当需要向 owner / Boss 做异步交接、保留分支说明或未完成风险交接时，再读取：

- `templates/handoff-template.md`

不要一开始就读所有模板；按选定的收尾路径加载。

## 何时使用

以下条件都满足时使用本技能：

1. 计划中的任务已完成
2. 局部验证已通过
3. 代码审查已完成，或准备进入最后一次全局审查

## 何时不用

1. 任务仍在实现中，尚未形成交付证据
2. 当前主要问题是需求没定、bug 未修完、关键测试未过
3. 只是想“顺手推一下代码”，还没有进入真正收尾阶段

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 关键测试未通过
2. 仍有未解释的本地改动
3. 仍存在未处理的严重审查问题
4. 用户尚未确认最终收尾路径

## 收尾工作流

### 1. 最终验证

至少完成：

1. 运行完整测试套件
2. 检查未提交的更改
3. 检查遗留调试代码、TODO/FIXME/HACK
4. 确认三层代码自文档已更新

### 2. 代码清理

重点清理：

1. 调试日志和临时输出
2. 注释掉的代码块
3. 临时开关、临时脚本、临时 mock

### 3. 全局代码审查

若任务由多个子任务组成，或使用过子代理开发，必须做一次整体视角审查：

1. 模块之间是否正确集成
2. 是否引入重复实现或风格割裂
3. 是否存在遗漏的收尾文档和风险说明

### 4. 选择收尾路径

向 Boss 展示四种收尾路径：

- `A`：创建 PR/MR
- `B`：合并到主干
- `C`：保留分支
- `D`：放弃分支

## 收尾路径选择矩阵

| 条件 | 推荐路径 |
|---|---|
| 团队协作、需要他人审查 | `A: 创建 PR/MR` |
| 个人项目、验证充分、准备直接收口 | `B: 合并到主干` |
| 功能已完成但仍需观察或等待业务确认 | `C: 保留分支` |
| 实验失败、方向放弃、确认不再保留成果 | `D: 放弃分支` |

## 输出要求

1. 无论选择哪条路径，都要说明交付证据、剩余风险和 owner
2. 选 `A` 时必须整理 PR 摘要
3. 选 `C` 或存在待确认事项时，必须整理 handoff
4. 选 `D` 前必须说明放弃原因与是否保留对比点

## 危险操作规则

以下操作必须在 Boss 明确确认后执行：

1. 删除分支
2. 强制删除 worktree
3. 直接合并到主干

## 收尾前最后一问

真正执行收尾路径前，必须再确认：

1. 当前结果是否已经具备交付证据
2. 是否仍存在未解释风险
3. 这个分支是否需要保留作为回滚点、对比点或后续继续开发点

## Git 最小示例

```bash
git push -u origin feature/功能描述
gh pr create --title "功能描述" --body "详细说明"
```

```bash
git checkout main
git merge feature/功能描述
git push
```

## Worktree 清理

如果使用过 worktree，收尾时必须确认：

1. 任务已合并或已明确放弃
2. worktree 中无未保存成果
3. 清理后 `git worktree list` 结果符合预期

## 完成定义

只有以下条件都满足，才算真正收尾完成：

1. 测试通过并展示了证据
2. 本地改动状态清楚
3. 调试代码已清理
4. 文档已同步
5. Boss 已确认最终操作路径
6. 选定路径已执行并反馈结果

## 禁止事项

1. 不要在测试未通过时开始收尾——未通过的测试 = 未完成的任务，收尾流程会掩盖真实状态
2. 不要把”创建 PR”和”直接合并”混成默认同一步——两者的审查义务、回滚成本完全不同
3. 不要在未确认时删除分支或强制清理 worktree——删除后无法恢复未推送的提交
4. 不要遗漏全局视角的回归检查——子代理各自通过测试不代表集成后仍然通过
5. 不要只说”已完成”却不给验证证据——没有证据的完成声明等于谎言
6. 不要在未加载对应模板时草率输出 PR 或 handoff——缺少模板约束会漏掉关键字段
7. 不要在 worktree 中有未保存成果时执行 `git worktree remove --force`——会永久丢失未提交改动
8. 不要在 merge 前跳过 `git diff main...HEAD` 检查——可能引入意外的 diff 或冲突残留
