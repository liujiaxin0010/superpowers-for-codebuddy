# 问题单修改方法论

基于问题单信息，通过上下文完整读取、精准定位、全面修改、严格验证的全流程方法论。

## 核心原则

1. **上下文完整**：修改前必须充分读取上下文，包括主文件完整内容、相关文件、数据定义、方法定义、相似代码等
2. **全面修改**：识别所有需要修改的位置，不遗漏引用点、相似点、对称点
3. **精准修改**：只解决当前问题，不修改无关代码
4. **最小化变更**：确保完整性的前提下，修改范围最小化
5. **必须确认**：不确定的方案必须用户确认
6. **遵循用户方案**：用户提供方案时，基于充分上下文验证正确性和完整性，补充遗漏
7. **修改前验证**：距离上次读取超过5条消息，必须重新读取文件确认内容
8. **修改后验证**：验证语法、逻辑、一致性和完整性，检查遗漏

## 何时使用

1. 用户提供了问题单（网址、截图、问题编号）需要定位并修复代码缺陷
2. 用户描述了具体的 bug 现象并要求修复
3. 代码审查产出的缺陷清单需要逐条修复

## 何时不用

1. 用户只是想了解代码逻辑，没有修复意图——应使用代码阅读或审查技能
2. 需求是新增功能而非修复已有缺陷——应走 spec/plan 工作流
3. 问题是架构级别的重构——应走重构工作流，而非逐点修补
4. 用户只提供了模糊描述（"系统有时候慢"）且无法复现——应先走排查定位流程

## 阻断条件

1. 问题描述不足以定位代码范围，且用户无法补充——阻断并说明缺失信息
2. 涉及的文件无法读取（权限、路径不存在）——阻断并报告
3. 修改方案涉及高风险操作（数据库 schema 变更、核心接口签名变更）且用户未确认——阻断等待确认

## 前置依赖

- **Chrome DevTools MCP**：仅当输入为网址时需要，用于页面实时检查
- **图片理解能力**：仅当输入为截图时需要

## 资源加载规则

当定位困难、修改点遍布多文件、或需要系统性排查时，再读取：

- `references/context-and-identification-checklist.md`

简单的单文件单方法修复不要预加载清单。

## GitNexus 加速上下文读取（优先路径）

如果 GitNexus MCP 可用（见 `.codebuddy/rules/gitnexus-code-intelligence.md` 的可用性检查），
优先使用以下方式替代手动逐文件阅读：

### 用户提供了文件时：
1. 使用 GitNexus **模式 A**（文件 360° 上下文）获取该文件的完整依赖图
2. 使用 GitNexus **模式 D**（调用链追踪）获取问题方法的上下游调用链
3. 根据返回的调用链，**仅精读**调用链上的关键代码段（不需要全文件阅读）
4. 如果 GitNexus 已覆盖调用关系，跳过 `search_content` 搜索步骤

### 用户未提供文件时：
1. 使用 GitNexus **模式 F**（语义搜索）根据问题描述定位候选文件
2. 使用 **模式 A** 确认候选文件的角色和关系
3. 如果无法确定，仅再向用户提出候选文件

### 降级处理：
GitNexus 不可用时，直接使用下方的手动"上下文分层读取策略"（原有流程不变）。

## 上下文分层读取策略

必读：主文件完整内容、涉及方法定义、数据定义、导入依赖。
扩展：调用关系、工具函数、接口定义、相似逻辑。

当定位困难或修改点复杂时，读取详细清单：

- `references/context-and-identification-checklist.md`

## 全面修改点识别

必查：主修改点、相关引用点、相似代码点、对称逻辑点、关联数据点、类型定义点、注释文档点。

排查方向：调用链、数据链、事件链、依赖链。从问题点向外逐层扩散。

## 修改方案输出格式

```
【问题单】: [问题单号(禁止从网址url上获取)] [描述]

【问题现象】: [现象描述]
【预期现象】: [用户提供的预期现象，如有]

【定位分析】:
- 涉及文件: [文件列表]
- 问题位置: [具体位置列表]
- 原因分析: [基于上下文的原因，允许多个，必须指出对应代码位置]
- 上下文范围: [已读取的上下文范围]

【修改方案】:
修改点N: [标题]
- 文件: [文件]:[行号]
- 当前: [代码(代码块)]
- 修改: [代码(代码块)]
- 原因: [为什么需要修改]
- 风险: [低/中/高]

[如需确认则标注]
【是否确认?】
```

## 修改前验证流程

1. **重新读取文件**：距离上次读取超过5条消息，必须重新读取
2. **精确匹配old_str**：确认唯一性，不唯一则扩大上下文范围；保留完整缩进、空格、换行、标点
3. **验证修改点完整**：确认无遗漏，每个old_str和new_str准确无误
4. **每个文件连续修改不超过3次**，超过则重新读取文件

## 修改后验证流程

1. **语法验证**：调用 `read_lints` 检查linter错误，有则立即修复
2. **逻辑验证**：检查修改后代码逻辑正确性，是否遗漏修改点，是否破坏原有功能
3. **一致性验证**：变量名/方法名一致、代码风格统一、注释是否需更新
4. **遗漏检查**：重新搜索相关关键词，确认所有位置都已处理

## 修改完成输出格式

```
修改完成
【修改点N】: [文件]:[行号] - [简述]
- 修改前: [代码(代码块)]
- 修改后: [代码(代码块)]

【统计】: 修改X个文件，X行代码
【建议】: [测试建议]
```

## 常见错误（必须规避）

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 上下文读取不足，只读问题附近片段 | 误判原因，引入新问题 | 主文件完整读取+相关定义+依赖组件 |
| 修改点识别不全，只改主位置 | 修改不完整，不一致 | search_content搜索所有引用，统一修改 |
| 修改前未重新读取文件 | old_str匹配失败，覆盖最新修改 | 超过5条消息必须重新读取 |
| 过度依赖用户方案，不验证 | 方案有误或不完整 | 基于上下文验证正确性和完整性 |
| 修改后不验证 | 语法错误、逻辑错误、遗漏 | read_lints检查+逻辑验证+遗漏检查 |

## 禁止行为

1. 不要在上下文不充分时就给出修改方案——片面信息会导致误判根因，修复后引入新问题
2. 不要遗漏相关修改位置只改主位置——不完整的修改会造成数据不一致或运行时错误
3. 不要未经用户确认就执行修改——用户可能有额外上下文或不同的修复偏好
4. 不要修改无关代码、添加新功能或重构优化——超出问题单范围的变更会引入不可控风险
5. 不要猜测不明确的信息——猜错会把整个修复方向带偏，应向用户确认
6. 不要忽略代码风格和格式——风格不一致会干扰后续 code review，增加合入阻力

## 特殊情况处理

| 情况 | 处理方式 |
|------|---------|
| 未提供文件 | 自动分析项目定位文件 |
| 信息不完整 | 列出缺失信息，询问补充或推测 |
| 无法定位 | 说明搜索结果，提供可能原因，建议补充信息 |
| 风险过高 | 明确风险点，建议测试环境验证 |
| 图片模糊 | 提示提供更清晰截图或网址替代 |

## 输入建议

- 问题单已有修改方案或结论：直接提供，AI 将验证并执行
- 不确定的定位原因：建议不提供，防止干扰独立分析
- 明确代码文件：一并提供，提升定位速度
- 接口参数修改：必须提供接口入参、返参示例
- 提供期望结果：明确描述修改后应有的效果
