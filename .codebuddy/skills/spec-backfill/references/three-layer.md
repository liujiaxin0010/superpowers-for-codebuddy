# 三层回填保障

```
即时回填（编码中）── 每日回填（Task#1 01:00）── 每周回填（Task#25 周一）
   代码变 Spec 变      扫 24h 提交差量          全量审视一致性
```

## 第一层：即时回填（编码过程中）

- 触发：AI 每次生成代码后，同步更新 `spec/` 下相关文档
- 重点：核心流程和接口定义
- 原则：代码变 → Spec 跟着变，不留偏差
- 落点：`/execute-plan` 内嵌 hook（见 `executing-plans` SKILL「即时规格回填」节）

## 第二层：每日回填（Task#1，每日 01:00）

**Step 1 — 获取最近提交**：`git log --oneline --since="24 hours ago"`

**Step 2 — 分析变更影响**：

| 提交类型 | 影响判断 | 文档操作 |
|---|---|---|
| `feat:` 新功能 | 检查是否已在 Spec 中描述 | 未描述 → 补充 |
| `feat:` 改已有功能 | 检查 Spec 描述是否与实现一致 | 不一致 → 更新 |
| `fix:` 修复面向用户行为 | 检查 Spec 行为描述 | 需更新 → 更新 |
| `refactor:` 纯内部重构 | 通常不影响 Spec | 不操作 |

**Step 3 — 更新 Spec**：读当前文档 → 在合适位置增改 → 保持现有风格 → 无需更新则不强行改

**Step 4 — 通过 MR 流程提交**：所有文档修改经 MR，CI 通过合并后才算完成

范围：`spec/` 下 README、核心流程、OpenAPI、配置设计、数据库设计。

## 第三层：每周回填（Task#25，每周一 10:00）

**Step 1 — 读现有文档**：读 `spec/` 全部文件，建当前文档状态心理模型

**Step 2 — 扫代码变化**：浏览本周主要变化（接口变更、新增/删除文件、架构变化、配置项变更）；用目录结构和修改时间判断范围，不逐文件读

**Step 3 — 更新文档**：

| 文档类型 | 策略 |
|---|---|
| 总览 README | 全量重写（反映系统当前真实状态）|
| 模块文件 | 增量更新（只改有变化的部分）|
| 新业务流程 | 创建新文件 |

**Step 4 — 自检**：

| 检查项 | 内容 |
|---|---|
| 流程图可渲染 | Mermaid 语法正确 |
| 功能完整性 | 覆盖所有用户可感知能力 |
| 术语一致性 | 同一概念用相同术语 |
| 无实现细节泄漏 | 无复述代码逻辑的段落 |
| 交叉引用有效 | 引用指向正确文件 |
| 无过时信息 | 已删代码不再被描述为「存在」|

**Step 5 — 通过 MR 流程提交**。

## 保障层：审查阶段同步检查

代码审查时同步检查 Spec 是否需更新，将 Spec 偏差视为技术债的一种。
