# 系统化调试

系统化调试的目标不是“快点给修复”，而是**先找根因，再做最小修复，再验证整个防线**。

## 资源加载规则

当需要从症状回溯到源头时，再读取：

- `root-cause-tracing.md`

当问题涉及异步时序、竞争条件或 eventual consistency 时，再读取：

- `condition-based-waiting.md`

当已经有修复候选，需要验证“症状层、根因层、回归层、预防层”时，再读取：

- `defense-in-depth.md`

当同一个问题修了 3 次以上仍失败时，再读取：

- `architecture-escalation.md`

当需要输出结构化调试结论时，再读取：

- `templates/debug-report-template.md`

## 调试纪律

1. 在完成“证据收集”前，不要提出修复方案
2. 设计不确定时先问 Boss，不要擅自扩展需求
3. 不写兼容性代码，除非 Boss 明确要求

## 四阶段协议

1. 收集证据：错误信息、最小复现、期望 vs 实际、最近变更、日志、问题边界
2. 形成假设：至少 3 个候选原因，按可能性排序，并给出验证方式
3. 验证假设：从最可能的开始，做最小验证实验，明确标记已排除项
4. 修复与验证：先写回归测试，再做最小修复，最后跑完整验证

## 4.5 架构反思

如果同一问题修复尝试失败 3 次以上，必须暂停补丁式修复，转入架构反思。

## 输出要求

结构化调试结果至少包含：

1. 问题描述
2. 证据收集
3. 假设与验证
4. 根因
5. 修复
6. 验证证据
7. 预防建议

## 禁止事项

1. 不要在没有复现或证据时拍脑袋修——无证据修复是赌博，修对了也不知道为什么对
2. 不要只修症状层，不验证根因层——症状修复会让真正的 bug 在生产环境爆发
3. 不要对异步问题用固定 `sleep(N)`——sleep 只是把竞争窗口从毫秒换成秒，不是修复
4. 不要连续失败 3 次后还继续原地打补丁——3 次失败说明心智模型有误，需要架构反思
5. 不要在修复后只跑失败的那一个测试——回归测试必须覆盖相关模块的完整测试套件
6. 不要同时改多处来"试试看哪个能修好"——多变量实验无法定位根因
