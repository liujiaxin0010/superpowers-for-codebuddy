# 并行交付（Parallel Delivery）

把长任务拆成多个低耦合 lane，并在合流前保持边界清晰、证据充分。

## 核心心智：lane = 持续边界，不是一次性分发

`parallel-delivery` 与 `dispatching-parallel-agents` 的根本区别：dispatching 是"给出去就等结果"的短暂并行；而 lane 是**持续维护的边界**——lane 有自己的生命周期（创建→执行→验证→合流→清理），需要持续跟踪状态、处理失败和维护契约。

选择本技能还是 dispatching 的判断：

| 信号 | 选择 |
|---|---|
| 子任务 < 30分钟，无需中间检查点 | `dispatching-parallel-agents` |
| 子任务跨越多个会话或需要阶段性验证 | `parallel-delivery` |
| 子任务有独立的验证命令和交付证据 | `parallel-delivery` |
| 子任务可能失败并需要独立回退策略 | `parallel-delivery` |

## 何时使用

- 一个任务可拆成 2 个以上低耦合子项
- 并行推进能明显节省时间
- 有明确 owner 负责最终集成和质量门禁

## 必备输入

1. 已批准的 `plan`
2. 子任务拆分
3. 每个子任务允许修改的目录
4. 每个子任务验证命令
5. 最终收口 owner

## 执行流程

1. 先检查子任务能否并行：
   - 不共享核心文件
   - 不互相依赖输出
   - 测试可独立运行
   - **若耦合判断不明确，必须先读取 `references/lane-checklist.md`，完成逐项检查后再继续**
2. 使用 `task-contracts` 生成 `parallel-delivery` 合同
3. 为每个 lane 写清：目标、边界、验证命令、依赖关系
4. Git 项目优先使用 `using-git-worktrees`——worktree 天然提供文件级隔离，普通分支切换会丢失构建缓存和 IDE 索引
5. 非 Git 项目使用独立 session，并严格限制文件边界
6. 所有 lane 结束后，由 owner 统一执行：
   - 冲突检查
   - 集成验证
   - `/code-review`
   - 质量门禁

## 耦合度检测协议

在分发前，必须对每对 lane 检查：

| 检查项 | 耦合信号 | 处理 |
|---|---|---|
| 两个 lane 修改同一文件 | 高耦合 | 合并为一个 lane 或串行 |
| 两个 lane 修改同一接口的不同实现 | 中耦合 | 可并行但合流时需接口兼容性测试 |
| 两个 lane 修改同一数据库表或共享状态 | 状态耦合 | 需要严格的读写顺序或锁协议，否则串行 |
| 两个 lane 的测试依赖同一端口/数据库 | 环境耦合 | 用不同端口/数据库或串行测试 |
| 两个 lane 无文件交集且测试独立 | 无耦合 | 安全并行 |

## 合流冲突解决

当 lane 合并到主干时：

1. 先合并无冲突的 lane
2. 有冲突的 lane 由 owner 逐个解决，每次解决后跑完整集成测试
3. 若冲突涉及共享契约变更（API 签名、数据模型、配置格式），必须回退到重新设计阶段——补丁式修复只会把不一致推迟到生产环境

## 阻断条件

- 多个 lane 同改同一核心文件
- 没有统一 owner
- 子任务拆分不清，仍然强耦合
- 只交代码，不交验证证据

## Lane 失败处理

| 情况 | 处理 |
|---|---|
| 单个 lane 失败，其他 lane 无依赖 | 其他 lane 继续，失败 lane 单独修复 |
| 单个 lane 失败，其他 lane 依赖其输出 | 暂停依赖 lane，等待修复 |
| 多个 lane 同时失败 | 暂停全部并行，回退到计划阶段 |
| lane 超时无响应 | owner 主动检查状态，超过预估时间 2x 视为失败 |

## 禁止事项

1. 不要在未做耦合度检测时就并行分发——并行冲突的返工成本远大于串行等待，且合并冲突往往在最后一刻才暴露
2. 不要让没有验证命令的 lane 开始执行——无法验证 = 无法收口，owner 在合流时只能盲信
3. 不要在合流时跳过集成测试——各 lane 独立通过不代表集成后通过，接口不兼容和状态冲突只有在集成时才会暴露
4. 不要让多个 lane 共享同一个 worktree——文件覆盖会导致静默数据丢失，且无法用 git diff 追溯哪个 lane 引入了哪个变更
5. 不要在 lane 合同中省略 `forbiddenPaths`——没有明确禁区的 lane 可能意外修改共享文件，导致合流时出现不可预期的冲突
6. 不要把 lane 的局部通过当成整体通过——每个 lane 的测试只覆盖自己的边界，跨 lane 的集成回归必须由 owner 在合流后统一验证
