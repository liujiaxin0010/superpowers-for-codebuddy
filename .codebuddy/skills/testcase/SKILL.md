# 测试用例

根据 `spec/AI2AI` 文档输出**可追踪、分优先级、覆盖高风险路径**的测试用例与覆盖分析。

## 输入

1. `spec/AI2AI/Design.md`
2. `spec/AI2AI/Architecture_Info.md`
3. `spec/AI2AI/Protocol_and_Data.md`
4. 可选：`spec/AI2AI/test.md`

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. `Design.md`、`Architecture_Info.md`、`Protocol_and_Data.md` 任一缺失
2. 设计文档没有明确目标对象、接口/数据边界或关键流程
3. 用户要求直接写自动化测试代码，而不是先产出测试用例文档

## 设计原则

1. 先覆盖风险最高的路径，再补常规路径
2. 每个核心需求、接口契约、状态流转都必须能追踪到至少一个用例
3. 用例验证业务行为，不把实现细节当断言目标
4. 同时覆盖正常、异常、边界、组合和回归视角
5. 产出的 Markdown 文档内容默认使用中文（代码、命令、路径、字段名可保留英文）

## 用例优先级

- **P0**：主流程成功、数据一致性、安全、权限、资金/状态变更、不可逆操作
- **P1**：常见分支、接口异常、边界输入、兼容组合、核心回归
- **P2**：低频场景、非关键提示、弱依赖功能、补充性健壮性检查

## 工作流

### 1. 提取测试对象

从输入文档中提取：

1. 功能点与用户场景
2. 关键接口和数据对象
3. 状态迁移、权限规则、异常分支
4. 外部依赖与失败模式

### 2. 先做覆盖矩阵

至少按以下维度建立覆盖矩阵：

1. 功能路径
2. 异常路径
3. 边界值
4. 状态切换
5. 多条件组合
6. 回归风险点

### 3. 标记高风险链路

下列情况必须单独列为高风险：

1. 涉及写操作、删除、迁移、批处理
2. 涉及认证、授权、隔离、数据脱敏
3. 涉及跨模块调用、异步流程、重试或幂等
4. 涉及复杂协议、格式校验、状态机

### 4. 建立追踪关系

每条核心用例都要能追踪回来源：

- 来源可以是需求点、接口契约、状态流转、风险项
- 没有来源映射的用例，默认视为低价值补充用例

## 输出契约

### 输出一：`spec/AI2AI/testcase.md`

每条用例至少包含：

1. 用例 ID
2. 优先级（P0/P1/P2）
3. 来源（需求点/接口/状态/风险项）
4. 前置条件
5. 输入/操作步骤
6. 期望结果
7. 覆盖类型（正常/异常/边界/组合/回归）

### 输出二：`spec/AI2AI/testcase_analysis.md`

至少包含：

1. 覆盖范围说明
2. 高风险链路清单
3. 覆盖缺口与原因
4. 用例数量统计（按优先级与覆盖类型）
5. 后续建议补齐项

## 推荐格式

```markdown
| 用例ID | 优先级 | 来源 | 场景 | 前置条件 | 步骤 | 期望结果 | 覆盖类型 |
|---|---|---|---|---|---|---|---|
| TC-P0-001 | P0 | 接口A + 风险R1 | 主流程成功 | ... | ... | ... | 正常/回归 |
```

## 禁止事项

1. 不要只写 Happy Path
2. 不要把“接口存在”或“页面可打开”当作完整用例
3. 不要遗漏权限、状态切换、幂等、错误输入这类高风险分支
4. 不要把实现细节、内部类名、私有方法当作测试目标
5. 不要输出没有来源追踪、没有期望结果的空壳用例
