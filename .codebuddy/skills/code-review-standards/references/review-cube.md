# 审查立方：三维度交叉评审 + 优先级

逐语言五维审查（正确性/性能/安全/代码质量/最佳实践）解决「单文件看什么」；本文件解决「整体不留盲区」——从三个独立维度做笛卡尔积，并用优先级决定先看什么。

## 1. 审查立方（3×3×4 = 36 项）

| 维度 | 取值 |
|---|---|
| 流程维度（验证实现过程）| 设计一致性 / 实现完整性 / 测试充分性 |
| 模块维度（验证结构边界）| 模块 A 内部 / 模块 B 内部 / 模块间（接口契约 + 数据流向）|
| 关注点维度（验证非功能属性）| 安全性 / 性能 / 规范性 / 可维护性 |

三维交叉形成 3×3×4 = 36 个审查项。单维度审查容易漏掉跨维度问题（如「实现了但测试不充分」「模块内部安全但模块间数据流不安全」），交叉能捕捉这类盲区。

```
        │ 安全 │ 性能 │ 规范 │ 可维护
────────┼──────┼──────┼──────┼───────
 设计    │  ✓   │  ✓   │  ✓   │  ✓
 实现    │  ✓   │  ✓   │  ✓   │  ✓
 测试    │  ✓   │  ✓   │  ✓   │  ✓
────────┼──────┼──────┼──────┼───────
 模块A   │  ✓   │  ✓   │  ✓   │  ✓
 模块B   │  ✓   │  ✓   │  ✓   │  ✓
 模块间  │  ✓   │  ✓   │  ✓   │  ✓
```

## 2. 维度与优先级（决定先看什么）

P0 必须全部完成；P1/P2/P3 按优先级覆盖，超时截断。

| 优先级 | 维度 | 关注点 |
|---|---|---|
| **P0** | 流程正确性 | 数据流完整性、错误处理缺口、边界条件 |
| **P0** | 安全性 | 命令注入、路径遍历、认证覆盖、密码处理、SQL 拼接、敏感信息硬编码 |
| **P1** | 架构合理性 | 分层清晰、职责单一、依赖方向 |
| **P1** | 并发安全 | 竞态条件、goroutine/异步任务泄露、死锁、共享数据保护 |
| **P1** | 错误处理与资源泄露 | 错误传播、资源清理、连接池/缓冲区释放、僵尸进程 |
| **P2** | 死代码 | 未使用的函数/变量/导入、废弃分支 |
| **P2** | API 契约一致性 | 接口格式对齐、请求/响应结构同步 |
| **P3** | 代码复用 | 重复逻辑提取、composable/util 复用 |
| **P3** | 硬编码值与魔法数字 | 分散的配置、硬编码端口/超时/阈值 |
| **P3** | 可观测性 | 关键路径日志、错误可追溯性 |

## 3. 审查检查点（维度的具体化）

| 编号 | 维度 | 检查项 | 级别 |
|---|---|---|---|
| 1 | 流程正确性 | 错误未处理或被忽略 | Critical |
| 2 | 流程正确性 | 错误信息缺少上下文 | Warning |
| 3 | 并发安全 | 异步任务泄漏（无退出机制）| Critical |
| 4 | 并发安全 | 共享数据未加锁/同步保护 | Critical |
| 5 | 并发安全 | 上下文未传递或未取消 | Warning |
| 6 | 错误处理与资源泄露 | 资源未正确关闭（文件/连接/响应体）| Warning |
| 7 | 错误处理与资源泄露 | 连接池/缓冲区未释放 | Critical |
| 8 | 架构合理性 | 函数签名过于复杂（>5 参数）| Info |
| 9 | 架构合理性 | 返回值不明确 | Info |
| 10 | 性能 | 循环内重复分配/序列化 | Warning |
| 11 | 性能 | 大对象不必要的拷贝 | Info |
| 12 | 规范性 | 公开函数/方法缺少文档注释 | Info |
| 13 | 规范性 | 命名不符合项目惯例 | Info |
| 14 | 安全性 | SQL 拼接（应使用参数化查询）| Critical |
| 15 | 安全性 | 敏感信息硬编码 | Critical |

> 级别映射到主报告的严重度：Critical→🔴 严重、Warning→🔵 一般、Info→🟢 提示。Critical 发现项必须同时创建 `.clawbench/issues/ISS-{nnn}.md`（见 `clawbench-issue-format.md`）。
