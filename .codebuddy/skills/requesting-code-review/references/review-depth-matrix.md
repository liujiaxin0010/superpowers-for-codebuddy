# 审查深度矩阵

本文件只在需要判断审查深度时读取。若主 `SKILL.md` 里的强制场景已经足够明确，不要重复加载本文件。

## 快速决策表

| 场景 | 默认深度 | 升级条件 | 不得降级 |
|---|---|---|---|
| 文档、小配置、注释修正 | 轻量 | 影响运行时行为、构建链路、权限、发布流程 | 缺验证证据时不能降级，只能 `BLOCKED` |
| Bug 修复 | 聚焦 | 跨模块、共享契约、安全、数据风险 | 缺复现或回归证据时不能发起 |
| 局部重构 | 聚焦 | 触及公共 API、共享模型、事务边界 | 需要证明“行为不变” |
| 功能完成、PR/MR、合并前 | 完整 | 涉及迁移、权限、支付、删除、并发 | 不要因为“文件少”就降级 |
| 子代理驱动开发、规格敏感任务 | 两阶段 | 可再叠加完整审查 | 不能降级成单阶段 |

## 轻量审查

适用：

1. 文档、注释、文案、低风险配置小改动
2. 明确不改变运行时行为

最小材料：

1. 改动范围
2. 改动目的
3. 基本验证或静态检查结果

升级信号：

1. 配置会影响构建、部署、权限、发布或默认开关
2. 涉及共享脚本、CI、生成流程

## 聚焦审查

适用：

1. Bug 修复
2. 局部重构
3. 影响范围小，但必须确认回归

最小材料：

1. 修复或重构范围
2. 复现方式、回归命令或行为不变证据
3. 希望 reviewer 聚焦的风险点

升级信号：

1. 触及共享契约、公共 API、共享模型
2. 带来安全、权限、数据一致性、并发风险

## 完整审查

适用：

1. 功能完成后
2. PR/MR 发起前
3. 合并到主干前
4. 跨模块、跨层级或多语言联动改动

最小材料：

1. 改动摘要
2. 审查目标
3. 文件列表或 diff
4. 已跑过的验证
5. 重点风险与待确认项

升级信号：

1. 迁移、权限、支付、删除、回滚、数据修复
2. owner 需要对整体耦合与回归面做把关

## 两阶段审查

适用：

1. `subagent-driven-development` 闭环
2. 明确需要“规格符合性 + 代码质量”双层把关
3. TaskContract 或 spec 已明确约束了目标边界

阶段要求：

1. Phase 1: `spec-reviewer` 检查是否偏离规格、越界、漏实现
2. Phase 2: `code-reviewer` 检查正确性、安全、测试、维护性

不得降级：

1. 不要把两阶段压成一次普通 code review
2. 不要在 Phase 1 未过时直接进入收尾

## 统一升级规则

出现以下任一情况时，不要选更浅的审查：

1. 共享契约、公共 API、共享模型发生变化
2. 涉及安全、权限、数据一致性、迁移、删除、回滚
3. 改动需要 reviewer 对整体集成结果负责
4. 验证证据不足
