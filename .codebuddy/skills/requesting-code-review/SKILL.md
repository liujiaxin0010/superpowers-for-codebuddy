# 请求代码审查

本技能用于判断：**现在是否必须审查、该走哪种审查、输出要长什么样。**

## 何时必须请求审查

| 场景 | 审查类型 | 必须？ |
|---|---|---|
| 子代理驱动开发中每个任务完成后 | 两阶段审查（spec-reviewer + code-reviewer） | **必须** |
| 重大功能实现后 | 完整代码审查 | **必须** |
| 合并到主干/main 之前 | 完整代码审查 | **必须** |
| Bug 修复后 | 聚焦审查（修复范围 + 回归） | **必须** |
| 重构后 | 聚焦审查（行为是否保持不变） | **建议** |
| 文档/配置更改 | 轻量审查 | **建议** |

## 审查类型选择协议

### 两阶段对抗审查

适用于：

1. `subagent-driven-development` 中的任务闭环
2. 明确存在规格与实现双层校验需求的场景

### 完整代码审查

适用于：

1. 功能完成后
2. 合并前
3. 需要从正确性、安全、测试、耦合整体把关时

### 聚焦审查

适用于：

1. bug 修复后
2. 局部重构后
3. 已知改动范围很小，但仍需回归确认时

## 资源与边界

1. 若审查是多语言通用审查，优先切到 `code-review-standards`
2. 若审查目标包含 `.vue/.js/.ts` 前端代码，叠加 `web-code-review`
3. 本技能负责“是否发起 + 用哪种审查 + 输出结构”，不负责展开完整的语言级审查规则

## 审查前最小条件

至少要明确：

1. 审查范围
2. 改动目的
3. 验证证据或验证命令
4. 当前任务结论是否已达成

若这些信息缺失，不要急着发起大审查，先补上下文。

## 输出要求

每条反馈必须包含：

1. 文件位置
2. 问题描述
3. 严重度
4. 修复建议或下一步动作

## 严重度组织

- 🔴 严重：必须修复，阻止继续
- 🟡 警告：建议当前迭代内修复
- 🔵 建议：记录改进方向，不阻止

## 禁止事项

1. 不要在没有改动范围和验证信息时发起完整审查
2. 不要把子代理任务的两阶段审查降级成一次普通审查
3. 不要把“请求审查”和“开始自动修复”混成同一步
4. 不要遗漏严重度和位置
5. 不要在前端代码审查中忘记协同 `web-code-review`
