# 并行代理分发

本技能回答的是：**现在能不能并行、应该怎么分组、每个子代理该拿到什么任务包。**

## 资源加载规则

当你不确定任务之间是否存在写集、依赖或测试环境冲突时，再读取：

- `references/parallel-conflict-matrix.md`

当已经确认可以并行、准备给每个子代理下发任务时，必须读取：

- `templates/subagent-task-packet.md`

当多个子代理完成后，需要由 owner 统一收口时，再读取：

- `templates/parallel-summary-template.md`

如果还没确认“能不能并行”，不要先加载模板。

## 何时使用

1. 计划中存在 2 个以上低耦合任务
2. 每个任务都能明确允许修改范围
3. 每个任务都有独立验证命令
4. 汇总阶段有明确 owner 收口

## 何时不用

1. 所有任务都改同一个核心文件
2. 多个任务共享同一契约，且顺序未定
3. 测试环境会互相干扰
4. 用户要求严格串行推进

## 与其他技能的边界

1. 若需要 lane 级长期管理、worktree 和 owner 收口，优先 `parallel-delivery`
2. 若每个任务还需要 implementer + 双阶段审查闭环，优先 `subagent-driven-development`
3. 本技能更适合“当前轮次内的并行分发决策”

## 阻断条件

出现以下任一情况时，返回 `BLOCKED`：

1. 无法确认任务之间的依赖关系
2. 无法明确每个任务的文件边界
3. 没有统一 owner 或集成负责人
4. 共享核心文件但又无法重新拆分任务

## 并行决策协议

1. 先按依赖把任务分成：完全独立、部分独立、必须串行
2. 再检查写集、共享状态、测试环境是否冲突
3. 默认最大并行度不超过 5；环境脆弱时继续降并行度
4. 每个子代理必须拿到任务包，而不是一句口头说明
5. 所有并行结果最终都由同一个 owner 统一收口

### 写集冲突快速检测

分发前必须回答以下问题，任一项为"是"则不可并行或需要重新拆分：

1. 两个任务是否修改同一文件的同一区域？
2. 两个任务是否修改同一接口/类型定义？
3. 两个任务是否会同时写入同一数据库表或配置文件？
4. 两个任务的测试是否依赖同一全局状态（端口、临时目录、单例）？

若不确定，运行 `git diff --name-only` 列出每个任务的预期修改文件，取交集判断。

## 输出要求

1. 若被阻断，明确说明是哪类冲突导致不能并行
2. 若可以并行，说明分组、每组 owner、每组验证命令
3. 下发子代理时必须套用任务包模板
4. 收口时必须给出冲突检查、集成验证和剩余风险

## 禁止事项

1. 不要因为”看起来能省时间”就忽略依赖关系——并行冲突的返工成本远大于串行等待
2. 不要让共享核心文件的任务并行——合并时的冲突解决几乎总是引入回归
3. 不要没有验证命令就并行分发——无法验证的子代理任务等于不可信的产出
4. 不要没有统一收口人就启动并行——无人集成 = 多个独立正确但整体不一致的结果
5. 不要把一次性并行分发误当成长期 lane 管理——短期分发用本技能，长期 lane 用 parallel-delivery
6. 不要在子代理任务包中省略文件边界——没有显式边界的子代理会踩入其他任务的修改范围
