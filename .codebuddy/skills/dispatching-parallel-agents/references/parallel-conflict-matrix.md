# 并行冲突矩阵

本文件只在“看起来能并行，但不确定会不会互相踩”时读取。

## 快速判断表

| 情况 | 能否并行 | 处理方式 |
|---|---|---|
| 写入文件完全不重叠 | 可以 | 直接并行 |
| 写入文件不同，但共享同一契约或生成物 | 谨慎 | 先拆前置批次，再并行后续 |
| 共享核心文件、公共配置、共享模型 | 不可以 | 改为串行或切成上游/下游 |
| 测试命令互不干扰 | 可以 | 保持独立验证 |
| 测试环境互相抢资源 | 不建议 | 降并行度或改串行 |
| 需要统一 owner 收口 | 必须 | 指定一个 owner 再启动 |

## 写集冲突

以下情况默认视为冲突：

1. 同时修改同一个核心文件
2. 同时修改同一份共享配置
3. 同时改公共模型、公共接口、公共 schema

不要被“只是几行改动”误导；共享文件就是共享风险。

## 依赖冲突

以下情况默认不要同轮并行：

1. B 任务依赖 A 任务本轮产出
2. 多个任务都等一份共享契约先定稿
3. 还没确定哪一条实现路线是主线

正确做法：

1. 先把上游独立做完
2. 再把下游低耦合任务并行展开

## 测试与环境冲突

以下情况需要降并行度或串行：

1. 共用数据库、端口、fixture、缓存目录
2. 测试会改全局状态
3. 构建或安装步骤会相互覆盖产物

## 何时升级到其他技能

1. 需要 lane 级长期管理、worktree、owner 收口时，切到 `parallel-delivery`
2. 需要 implementer + 双阶段 review 闭环时，切到 `subagent-driven-development`
