# 需求规格列表（Requirement Spec）

本技能回答的是：**怎样把需求写成 AI 能直接据以生成代码的结构化规格，让模糊与矛盾在进设计前就消除。**

## 核心心智：规格清晰度决定 AI 生成质量

AI 无法弥补规格本身的模糊与矛盾——它不会「猜」意图，只按字面理解规格生成代码。

1. **关键决策显式声明**：写入模式、并发策略、错误传播路径等，不留白让 AI 推断
2. **矛盾优先解决**：规格内部或规格间的矛盾，必须在进设计前解决
3. **边界条件前置声明**：数据为空时的行为、重试上限、超时阈值等，越早声明越好

## 资源加载规则

- 写需求规格列表时，读 `templates/requirement-spec-list.md`
- 做需求评审或结构合规检查时，读 `references/three-tier-review.md`

## 何时使用

1. 需求分析阶段输出「需求规格列表」（开发背景 + 功能描述）
2. 已有粗略需求，需要结构化为分层功能清单 + 边界条件
3. 需求评审前按三级（子系统/子组件/子模块）自检

## 何时不用

1. 需求高度模糊、方向未定 → 先 `/brainstorm` 发散澄清
2. 模拟真实评审会上会自检 → 用 `/requirement-review`
3. 已实现代码与需求的差异核对 → 用 `/requirement-coverage`

## 产出物

需求规格列表（`docs/specs/{date}-{slug}-requirement-analysis.md` 或 `spec/{子组件}/需求规格.md`）：开发背景 + 分层功能清单 + 边界条件前置 + 接口规格前置 + 设计变更追溯。

## 与相邻技能的关系

```
/brainstorm（发散澄清）→ requirement-spec（结构化规格）→ /requirement-review（评审模拟）→ /spec-lite
                                                          → 实现后 /requirement-coverage（覆盖核对）
```

## 关键实践

- **分层功能清单**：按「模块→功能点→描述→依赖→实现状态」五列表系统化梳理，每个功能点标依赖和实现状态（📋规划中/🚧开发中/✅已实现），AI 可据此判断开发优先级
- **接口规格前置**：需求阶段就引用外部 SDK 接口定义，明确接口契约，避免设计阶段再补
- **设计变更追溯**：文档顶部标注重要设计变更，文末专设「已移除的功能」章节记录移除原因和替代方案，确保 AI 不生成已废弃功能的代码

## 禁止事项

1. 不要把关键决策留白——模糊规格必然导致偏离预期的实现
2. 不要带着矛盾进设计阶段——矛盾会让 AI 产生不一致行为
3. 不要把边界条件留到设计阶段让 AI 推断——空值/越界/超时行为需求阶段就声明
4. 不要写实现细节——需求规格说「要什么」，不说「怎么做」
